## 2026-10-15 — USB hardware availability

The user retained full general-purpose USB forwarding and enrolled plug-and-play scope, but left the board/debug probe undecided because little hardware is available. Keep discovery, enrollment, exclusive ownership, permission loss, detach/reattach and reconciliation in the implementation scope. Record missing physical coverage explicitly; it is not permission to claim every USB class/device works. P0-S5/CAP-USB must distinguish reviewed provider/API/software evidence from actual attach/reset/programming tests. P0-S1 may record an unavailable target rather than invent one; unrelated Android and Linux-host work continues.

## 2026-10-15 — USB implementation entry

P0-S5 is active on its existing P0-S1 prerequisite. The [provider entry](../03-platform/googlebook/p0-s5-usb-provider-entry.md) keeps three separate boundaries: Android grant-owned device access, network export, and workstation import. The [reviewed real native access diagnostic](../06-validation/2026-10-15-native-usb-review.md) does not implement the latter two. libusb is reused for the Android FD boundary; usbredir's QEMU/SPICE guest topology does not silently replace the selected bare Linux workstation. VirtualHere remains an external candidate whose exact Android control/terms, consumer access and authenticated transport need qualification. Missing representative hardware retains R02/R20 and CAP-USB pending; no board selection is requested again.
