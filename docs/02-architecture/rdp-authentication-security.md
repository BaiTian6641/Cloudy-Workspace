# Native RDP authentication and credential security

**Status:** proposed implementation contract, researched **2026-10-15**. **Owners:** Desktop/Android security and native integration developers. **Stages:** P0-S4 establishes engine boundaries; P1-S3/P1-S4 implement and review app identity/storage; P3-S7 qualifies the product. This document adds no device pass or completed vault. Read with [security and lifecycle](security-and-lifecycle.md), [desktop backends](remote-desktop-backends.md) and [P3](../05-delivery/phases/p3-desktop.md).

## Standard server boundary

Cloudy Desktop is a normal RDP desktop client. Direct connections use the selected maintained FreeRDP engine; RD Gateway is a separate optional connection route. Neither requires Cloudy Console, a proprietary Cloudy host agent, or a permanently running shared daemon. Relative pointer mode is an input capability to negotiate and qualify independently of authentication. A connection profile must not claim that a server supports it merely because ordinary pointer input works.

| Host lane | Contract and qualification boundary |
| --- | --- |
| Windows | Connect to an enabled, authorized RDP server on a supported Windows edition/configuration. Microsoft distinguishes client OS hosting from Windows Server/RDS deployments; edition, licensing, session, domain and administrative policy restrictions remain server prerequisites. No Windows qualification follows from Linux results. |
| Linux | Connect to an installed compatible RDP server, recording its version, authentication backend, desktop/session model and capture/input authorization. KRdp, xrdp and other implementations are separate server lanes; support for one does not establish the others. |
| macOS | Apple's documented screen-sharing route is VNC-compatible screen sharing, not evidence of an Apple RDP server. RDP hosting needs a separately selected, maintained third-party server with its own license/security/capture/input qualification. Until selected and tested, show RDP hosting unavailable and offer the independently qualified VNC route where applicable. |

References checked 2026-10-15: [Microsoft supported remote-PC configurations](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/remote-desktop-supported-config), [Apple screen sharing](https://support.apple.com/guide/mac-help/share-the-screen-of-another-mac-mh14066/mac). These establish platform boundaries, not Cloudy interoperability results.

## Authentication inventory and downgrade policy

| Method or identity | Product treatment |
| --- | --- |
| Username/domain/password with NLA/CredSSP | Initial implementation lane. Keep user, domain and account syntax distinct; preserve server rejection without retrying alternative identities automatically. The existing finite diagnostic is evidence for its exact password/NLA fixture only. |
| Kerberos or NTLM within CredSSP | Negotiation belongs to the maintained engine and actual server policy. Inventory the selected native build's providers and credentials before claiming Kerberos, domain SSO or enterprise compatibility. No automatic NTLM fallback if a profile explicitly requires Kerberos. |
| TLS-protected server logon without NLA | Optional, separately reviewed server compatibility policy; never silently downgrade from a required NLA profile or enable legacy RDP security because authentication failed. |
| Smartcard/certificate logon, Remote Credential Guard, restricted administration, Microsoft Entra/web authentication, gateway MFA | Explicitly unsupported until an official engine/API path, build capability and real server workflow are qualified. A host supporting a method does not establish Android adapter support. Android biometric approval unlocks local secret use; it is not remote Windows Hello or an RDP authentication method. |
| Gateway credentials | Separate credential reference and trust identity from the target desktop. Reuse target credentials only through an explicit profile choice and after both applicable identities are verified. |

CredSSP uses TLS and SPNEGO, with Kerberos or NTLM, and delegates credentials to the target server. Consequently, a malicious accepted server remains a consequential credential risk. Cloudy reuses the maintained protocol implementation rather than constructing TLS/CredSSP itself. [Microsoft MS-CSSP relationship to other protocols](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cssp/78e0d50f-5a99-45e8-9f8b-d8a2bd67d4eb), checked 2026-10-15.

## Verify the endpoint before releasing credentials

Bind trust to the canonical configured server name and port, protocol and route role (target or gateway). Keep the logical TLS name distinct from an IP transport address, tunnel address or gateway address. Editing an endpoint, redirecting to another target or changing route identity invalidates the old trust/credential binding until reviewed; never transfer a pin by display-name match.

The product must implement two explicit identity policies: normal certificate-chain/hostname validation through the selected engine's verified trust path, and an explicitly enrolled SHA-256 leaf-certificate pin for a private endpoint. Both reject expired/not-yet-valid certificates. Pin enrollment requires comparison through a trusted independent channel; first observation alone is not verified identity. Pin changes stop connection before password release, show old/new identity metadata, and require deliberate replacement or cancellation. No accept-all, certificate-ignore, trust-on-every-retry or fallback from pin mismatch to CA/known-host acceptance is permitted. An expired pinned certificate needs renewal/re-enrollment, not an ignore switch. Pinning alone does not promise revocation checking; the CA path must document its actual revocation behavior.

The diagnostic's external-certificate callback is a strict leaf-pin route, not a product CA validator. Preserve fail-closed callback behavior on malformed PEM, endpoint mismatch, exception or allocation failure. When adding a CA mode or gateway, review every TLS callback and credential-release path; do not assume target verification also verifies the gateway. The selected [FreeRDP source](https://github.com/FreeRDP/FreeRDP/tree/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc) and authored patches remain the implementation authority, with the exact package bindings in the P0-S4 evidence.

RD Gateway introduces another TLS-authenticated endpoint and gateway authorization, including server-configured connection/resource policies. Qualify the HTTPS gateway certificate and target RDP identity separately, and expose which stage rejected access. Gateway use is optional and cannot be replaced by opening an unprotected direct route after failure. [Microsoft RD Gateway deployment](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remote-desktop-gateway-role), checked 2026-10-15.

## Secret lifetime and saved credentials

The default is **ask for this connection**: hold a password only for the current connection attempt/session owner; do not persist it in profiles, journals, saved instance state, ViewModel restoration, command lines, environment variables or intent extras. The diagnostic's private operator-provisioned plaintext configuration is a temporary qualification fixture, not the product storage design.

Saving requires an explicit **Save on this device** action identifying account and endpoint. Use an opaque credential ID in the non-secret profile. Keep the secret and sensitive account metadata in the owning app's encrypted vault. A vault API exposes a scoped use operation to the session owner, not general plaintext reads to renderers, plugins or other packages. Console and Desktop have different app data and Keystore aliases; shared source and a handoff do not share secrets. Profile exports contain no secret or usable vault token; imported references require local enrollment.

Proposed record format: bounded versioned envelope containing random record ID, key alias/version, algorithm identifier, IV and authenticated ciphertext/tag. Generate AES-256 with the `AndroidKeyStore` provider and use `AES/GCM/NoPadding`, a fresh provider-generated IV for every encryption, and a 128-bit tag. Authenticate immutable format version, owning package, record ID, endpoint/role and account-binding metadata as additional authenticated data before processing plaintext. Do not reuse an IV, accept unauthenticated partial output, or substitute plaintext on errors. Serialize record updates, write atomically, and reject oversized, unknown-version, truncated or tampered records. Endpoint edits require a new authorized binding rather than silently changing authenticated metadata.

The Android Keystore protects the AES key, not arbitrary password objects. Hardware protection is conditional on the device, algorithm and generated key; inspect `KeyInfo.getSecurityLevel()` on API 31+ and report software/TEE/StrongBox accurately. On API 23–30, `isInsideSecureHardware()` supplies only the older hardware-backed boolean; do not infer StrongBox from it. The method-level API reference controls the runtime guard despite the guide’s target-SDK wording. StrongBox preference is optional; unsupported StrongBox must not trigger silent loss of a requested hardware-only policy. A user requiring hardware protection can keep per-session entry if the device cannot meet it. [Android Keystore guide](https://developer.android.com/privacy-and-security/keystore) and [KeyInfo method availability](https://developer.android.com/reference/android/security/keystore/KeyInfo#getSecurityLevel()), checked 2026-10-15. AES/GCM/provider compatibility and reported backing require actual-device qualification.

## Local authentication and recovery

For API 30+, require a secure device lock for saved secrets. Generate the vault key with `setUserAuthenticationRequired(true)` and `setUserAuthenticationParameters(30, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL)`. This proposed 30-second authorization window allows a narrowly bounded transaction; it is not per-operation hardware confirmation. Every new connection using a saved secret still requires a fresh foreground app approval and a one-use session authorization, even if the key's Android authorization window has not expired. Do not cache decrypted secrets for that window. API 23–29 may support other Keystore policies, but this contract falls back to per-session entry there until a separately reviewed local-auth route exists. [KeyGenParameterSpec.Builder API contract](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder), checked 2026-10-15.

Use AndroidX `BiometricPrompt`, `setAllowedAuthenticators(BIOMETRIC_STRONG | DEVICE_CREDENTIAL)` and matching `BiometricManager.canAuthenticate` checks. With the chosen time-based key, perform the cryptographic operation after successful prompt completion; do not mix it with a per-use `CryptoObject` flow without a separate design. Prompt cancellation, unavailable authentication, stale session generation or lifecycle cancellation releases no secret and starts no connection. System authentication UI must remain usable from a narrow desktop window. [Android biometric authentication guide](https://developer.android.com/identity/sign-in/biometric-auth), checked 2026-10-15.

If keys disappear or become permanently invalidated, ciphertext is not recoverable by Cloudy: preserve non-secret profiles, mark the credential unavailable, and ask the user to re-enter/re-save. Do not replace a key and mislabel the old record decryptable. Explicit credential deletion removes the record and its dedicated key alias; deletion cannot promise physical erasure from flash or previously compromised memory.

Credential Manager supports app sign-in credentials, passkeys and federated identity. It is not selected as a generic vault for arbitrary RDP host/account passwords: the Android app identity, provider association and sign-in retrieval model do not by themselves supply endpoint-scoped remote-server storage. Reconsider only with a concrete documented provider/server integration and explicit user consent; do not upload RDP passwords to a credential provider as an incidental implementation choice. [Credential Manager overview](https://developer.android.com/identity/credential-manager), checked 2026-10-15.

## Private storage, backup and observability

Store vault envelopes in credential-encrypted app-private `Context.getNoBackupFilesDir()` storage (API 21+), unavailable before user unlock. Do not use device-protected storage, shared/external storage, cache exports or content providers for secrets. The public API excludes this directory from automatic remote backup. [Context storage API](https://developer.android.com/reference/android/content/Context#getNoBackupFilesDir()), checked 2026-10-15.

Set `android:allowBackup="false"` as defense in depth; also declare `android:dataExtractionRules` on Android 12+/target 31+ excluding credential-bearing files/databases/preferences from both `cloud-backup` and `device-transfer`, plus `android:fullBackupContent` exclusions for older applicable versions. Maintain the actual path list when storage changes. Android documents manufacturer-dependent device-transfer behavior despite `allowBackup=false`; therefore verify exclusion on the intended distribution/device route and never treat that flag alone as sufficient. Restore must tolerate missing keys and require re-enrollment; no backup exports a recoverable secret. [Android backup rules](https://developer.android.com/identity/data/autobackup), checked 2026-10-15.

Logs, crash reports and journals contain bounded stage/error codes, opaque session IDs, engine versions and counters. Exclude passwords, hashes usable as credentials, NTLM material, tokens, PEM bodies, private keys, clipboard contents, typed text and full connection arguments. Treat hostnames/usernames as personal metadata: redact them in routine diagnostics and preview deliberate exports. Review native engine verbosity/error callbacks too; app-level redaction does not sanitize native logging automatically. Disable secret-screen screenshots/task previews through applicable public window APIs after UX review, while preserving accessible native password entry. Do not route local password entry to the remote keyboard stream or clear the user's unrelated clipboard.

## Session ownership and capability consent

Decrypt only after endpoint/profile validation and foreground authorization, then transfer the minimum necessary value to the native authentication callback. Wipe mutable buffers and release references promptly after use. JNI/Java immutable strings, native engine copies and remote credential delegation mean complete memory zeroization cannot be promised; retain ownership until native shutdown and release the settings/context through the maintained cleanup path.

Focus loss releases held input and pointer capture; it does not grant background vault access. Activity recreation may reattach to the same owned connection without another decrypt, but restored process state never auto-connects. Default last-window background behavior disconnects until a separately qualified visible continuous-session policy exists. Device lock or explicit vault lock stops input, clears pending local authentication, and disconnects under that default. A remote locked desktop is a separate server state. Reconnect requiring new credentials requires new foreground authorization; retries are bounded and never loop after authentication rejection. Disconnect closes input admission, requests cancellation, joins the native thread off the callback/main thread, and frees the instance only after ownership permits it. A timeout remains cleanup-pending rather than a fabricated free/join success.

Clipboard synchronization, drives/filesystem shares, printers, microphone, camera, smartcards and USB redirection default off. Enable only a supported, explicitly chosen capability scoped to the target profile/session, with Android permissions at use time. Imported RDP files, server requests and saved secrets cannot enable redirection implicitly. Audio output has its own visible preference. Drive sharing does not grant arbitrary storage access; ordinary SFTP remains independent. Disabling a capability must stop its actual channel and revoke ongoing access where the backend permits; otherwise reconnect with it disabled and explain the limitation.

## Host consent is separate from authentication

Successful TLS/NLA authenticates the RDP connection; it does not grant compositor screen/input access. On the qualified Linux portal route, the normal system prompt must actually be approved by the host user. General authorization to test is not evidence that the portal grant exists. Keep denied, pending and granted states distinct; do not modify permission stores or bypass compositor checks to make a test pass. The [portal run](../../qualification/results/P0-S4/2026-10-15-rdp-relative-portal.md) observed input only after consent.

Portal restoration tokens are authorization-bearing state. The finite fixture scopes XDG configuration/state privately and removes its owned restoration state, temporary key/configuration and route at teardown. Product host enrollment needs its own explicit persistence/revocation policy. A granted screen/input session also does not prove a protocol feature is implemented: the observed relative capability flag did not produce cursor movement on this server. Maintain the local release action even when remote input is ineffective.

## Threat limits and acceptance boundary

This design reduces exposure from copied app files, accidental backups/logs, stolen locked-device access and endpoint substitution. It does not protect plaintext after a compromised app/OS/native engine can use it, prevent an accepted malicious server receiving delegated credentials, certify remote session isolation, or establish protection from every accessibility/IME/screen-capture actor. Authentication approval is not consent to every remote action. Uninstall/data-clear, lock-policy changes and damaged vault records may make saved secrets unavailable.

Before product claims, qualify the changed boundaries: actual key backing/authentication cancellation and invalidation; ciphertext/metadata tampering and no plaintext fallback; applicable backup/transfer exclusion; pin-change/wrong-host/expiry rejection before credential release; native log redaction; concurrent-window ownership/process restoration; disconnect/reconnect secret lifetime; and disabled/consented redirection on each supported server lane. Reuse established engine validation, expanding only for a concrete adapter risk. Documentation, compiler success and diagnostic password/NLA results do not certify the vault, gateways, Windows/macOS interoperability or a security audit. The source/API register and backlog track this contract through API15, D15 and Q-S02.
