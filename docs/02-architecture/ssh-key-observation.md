# Credential-free SSH host-key observation

This is a bounded P1-S3 construction contract under CAP-FOUNDATION. The current source performs a real direct transport observation and offers an explicit owning-app trust-ledger update. It does not establish a completed SSH handshake, authentication, terminal, SFTP session, engine adoption or supported remote capability. Build and physical-device acceptance belong to their separately recorded evidence; this document makes no unrun-device claim. Read with [SSH host trust](ssh-host-trust.md), [connection profiles](connection-profiles.md) and [security/lifecycle](security-and-lifecycle.md).

## Identity and transport addresses

A selected committed SSH profile is bound by owning app, profile-store generation, profile ID/revision, label, protocol and canonical logical host/port. The direct route is explicit. Profile identity, trust-ledger generation/revision, transport address and window identity remain separate. Resolution never rewrites the logical peer or establishes reachability/trust.

`SshAddressResolver` consumes `SshPeerIdentity`. Canonical IPv4 and expanded IPv6 literals use Android [InetAddresses.parseNumericAddress](https://developer.android.com/reference/android/net/InetAddresses#parseNumericAddress(java.lang.String)), which performs no DNS lookup; reverse lookup is not used. Explicit scoped literals fail with `UNSUPPORTED_SCOPE`, rather than stripping a zone or resolving an interface name. Hostnames use the asynchronous A/AAAA [DnsResolver.query](https://developer.android.com/reference/android/net/DnsResolver) API on the application's default network, without changing global network selection. API37 uses `DnsResolver(Context, Looper)` with application context; min35–36 use guarded `getInstance()` fallback. The selected compile37 SDK exposes both signatures.

One process-wide HandlerThread handles query submission, callbacks and deadline work. Admission is bounded to sixteen active requests; results expose at most sixteen immutable numeric candidates with provider-attached names removed. Each request has an explicit cancel handle and a 1–30,000ms deadline, default5,000ms. Its atomic terminal gate selects one result, removes the deadline callback, signals Android [CancellationSignal](https://developer.android.com/reference/android/os/CancellationSignal) cancellation and discards late results. Result delivery is asynchronous on the main thread and must remain nonblocking. Cancel cannot retract a result already selected for delivery: the Activity independently checks its live operation marker and foreground lifecycle. Closing a resolver cancels its owned work and rejects later requests. Timers do not wake a suspended device; elapsed-time checks prevent an overdue successful result from being accepted.

## Android network permission boundary

Local-name/private-address classification is a prompt hint, not route authority or a trust grant. The adapter inspects the active network's capabilities and automatically suggests local-network permission only for known local candidates on a broadcast-network hint. VPN, cellular and unknown routes do not impose this preflight. The official [ACCESS_LOCAL_NETWORK definition](https://developer.android.com/reference/android/Manifest.permission#ACCESS_LOCAL_NETWORK) excludes VPN and cellular. Active-network capabilities are a snapshot rather than proof of every destination's route; Android enforces the actual operation. A manual permission entry remains available when automatic hints are insufficient.

The permission prompt retires the current attempt. Its callback never restarts DNS, observation or enrollment; the user must select/start a fresh check. Permission denial and transport failure remain honest unavailable/failure outcomes. Local permission is neither server identity verification nor authentication authorization. Loopback/USB-forwarded qualification, if performed, must be labeled accordingly and cannot certify a LAN permission path.

## Selected engine and signed-key boundary

The adapter reuses selected SSHJ0.41.2 mechanisms, public-key serialization and signature validation. Its initial policy permits only `ecdh-sha2-nistp256` KEX, `ecdsa-sha2-nistp256` server signature/key, `aes128-gcm@openssh.com`, `hmac-sha2-256` and no compression. The `ext-info-c` negotiation marker is allowed; it is not another KEX fallback. Domain support for other trust-key encodings does not enable their negotiation. Empty/unavailable selected factories and negotiated mismatches fail closed; there is no legacy fallback or custom parser/cryptographic implementation.

The finite worker receives an already resolved numeric `InetAddress` and connects using its numeric address and the logical peer's port. Candidates share one ten-second transport budget, additionally capped by the domain attempt expiry. Only a plain connect failure may advance to another candidate; an observed key, policy rejection, timeout, cancellation or uncertain cleanup stops fallback.

In the selected SSHJ KEX path, server signature verification precedes the host-key verifier. The verifier checks the numeric endpoint/port and active attempt, serializes the public key through SSHJ, derives its SHA256 fingerprint and **always returns false**. A key is therefore observed after verification of the KEX signature but before the client sends NEWKEYS; the server can send its own NEWKEYS first, so this is not a completed client handshake. No username, password, private key, agent, credential vault, authentication or session API is supplied or called. A signed response proves possession of the offered key, not that the unknown server is trusted. Independent fingerprint comparison remains necessary.

## Retirement and pinned implementation dependency

`SshHostKeyObserver` owns one socket, a deadline/cancellation watcher and the selected SSHJ client for each attempt. Socket registration rechecks cancellation/deadline so a concurrent stop cannot leak a newly created socket. Socket closure precedes client shutdown. Because SSHJ close can wait on transport locks, close runs in a tracked daemon helper; socket, watcher, close helper and Reader retirement share one finite two-second cleanup budget. Interrupts trigger cancellation and are restored on the owning worker.

Reader retirement deliberately depends on the **exact selected SSHJ0.41.2 source**, not a generic SLF4J contract. The private logger factory returns NOP loggers except for the selected Reader's exact `debug("Stopping")` terminal hook. That hook records the actual Reader Thread without publishing log content; the adapter then joins the Thread rather than treating a log event alone as retirement. `SSHClient.doKex` marks Reader expectation after `TransportImpl.init` starts it. Missing/changed hooks, wrong threads, unchecked setup failures, incomplete close or budget exhaustion cannot produce a successful observation: the outcome is `CLEANUP_UNCERTAIN`, and the shared observer instance is quarantined against reuse. A new Activity does not reset quarantine.

This dependency must be reviewed when changing the pinned engine or logging implementation. It neither authorizes broad engine logging nor assumes abnormal VM failures run cleanup. The selected source is retained as local research evidence; public source references and dependency decisions are tracked by the integration leader. See the [SSH investigation ADR](../adr/0011-ssh-terminal-investigation.md) and [library reuse policy](../05-delivery/library-reuse-policy.md).

## Foreground comparison and persistence

The in-memory `SshObservationPresentation` policy issues an identity-bound attempt only after explicit foreground selection/check. It rejects stale ticket references, owner/peer mismatches, changed profile generation/revision/fields, backwards time and exact deadline expiry. An attempt lasts at most120seconds. A successfully completed unmatched observation creates a distinct presentation generation with its own at-most120second lifetime; these are separate deadlines, not one combined120second allowance.

The native comparison shows the exact logical host, port, direct route, observed key/fingerprint, previous key where applicable and expected trust revision. First use, replacement and reenrollment after revocation remain distinct. Title/explanation/identity scroll together while actions remain separate. The immutable challenge is a persistence proposal, not authorization to continue a connection. Match ends observation without an approval; saving requires a separate deliberate action, fresh committed-profile reload and one policy admission followed by the exact owning trust-store generation/revision CAS. Concurrent trust edits/revocation cause stale-CAS denial.

Pause, save-state, cancellation, superseding selection and destruction retire attempts/challenges. No selection, key, attempt, deadline or approval is restored. Before mutation admission, the Activity records a pending bit; a stale callback or restored pending state is completion-uncertain and cannot replay the write. An admitted CAS may finish after pause, so cancellation does not promise rollback. Explicit Refresh reconciles actual committed state; it does not reuse the old challenge. Saving a pin does not authenticate, reconnect or resume: another observation requires a fresh user action.

## Required continuation and acceptance limits

Source owners are the domain `SshObservationPresentation.kt`; platform `SshAddressResolver.kt`, `SshLocalNetworkPolicy.kt`, `CloudySshObserveActivity.kt` and `SshObserveScreen.kt`; and the `shared/android/ssh` observer/policy/codec/cancellation/retirement classes. Meaningful adapter acceptance must cover real signed-key observation, cancellation/deadline/socket retirement, stale/lifecycle denial, exact trust CAS, uncertainty, and preservation of unrelated owning-app data. Offline numeric tests cannot certify DNS-provider behavior; a loopback fixture cannot certify Android LAN enforcement.

Full SSH remains required: broader reviewed algorithm policy, credentials bound to the exact owning vault, a fresh connection with actual presented-key revalidation before any authentication gate, ordering against revocation/cancellation, live-session rekey/revocation handling, independently verified ordered jump hops, authentication, terminal/session lifecycle, tunnels, separate X11 windows and session-linked SFTP/drop. See [P2 Console scope](../05-delivery/phases/p2-console.md). None of those capabilities follows from saving an observed key or passing this finite observer boundary.
