## Proposed key and certificate adapter

Use `KeyStore.getInstance("AndroidKeyStore")`, `load(null)`, and a serialized identity-enrollment operation off the main thread. Generate RSA2048 through `KeyPairGenerator.getInstance("RSA", "AndroidKeyStore")`. Use an opaque, versioned app-owned alias, independent for the diagnostic and eventual Desktop package; no host/account names in aliases or logs. Retrieve the private handle using `getKey(alias, null)` or `PrivateKeyEntry`; never serialize it or construct `PKCS8EncodedKeySpec`. The implementation may call `getEncoded()` solely as an explicit non-exportability qualification: require null, and wipe/reject any unexpected returned bytes without saving or returning them. [Android's Keystore guidance](https://developer.android.com/privacy-and-security/keystore) documents app-local credentials, non-exportability and hardware-dependent protection; non-exportability alone does not prove hardware backing or prevent a compromised app from using its key.

Proposed generation authorizations, subject to actual-device TLS verification:

```text
purpose: PURPOSE_SIGN
keySize: 2048
signaturePaddings: SIGNATURE_PADDING_RSA_PKCS1, SIGNATURE_PADDING_RSA_PSS
digests: DIGEST_NONE, DIGEST_SHA256, DIGEST_SHA384, DIGEST_SHA512
encryptionPaddings: ENCRYPTION_PADDING_NONE
userAuthenticationRequired: true
userAuthenticationParameters: 30 seconds, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL
unlockedDeviceRequired: true
```

`KeyGenParameterSpec.Builder`, RSA padding/digest authorization and key-size setters are API23; timed authenticator parameters API30; unlocked-device restriction API28. This entry targets the Googlebook/API37 route; older identity routes remain unavailable until reviewed. The implemented identity store admits API37 only and locally guards `KeyInfo.isUnlockedDeviceRequired()`, whose public inspection API was added in36.1 (G145); the generation setter itself is API28. The APK minimum need not be raised for unrelated native-load functionality. No `PURPOSE_ENCRYPT` or `PURPOSE_DECRYPT` is needed. Authorizing `DIGEST_NONE` is important for TLS, whose stack may prehash before signing. See the [Builder contract](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder). The candidate includes SHA-384/512 and PSS for modern TLS signature choices, not a claim that a specific server negotiated them. Do not add arbitrary legacy signing algorithms on failure.

The `ENCRYPTION_PADDING_NONE` authorization has a specific TLS compatibility reason, not application-level unpadded encryption. Official [Conscrypt CryptoUpcalls](https://github.com/google/conscrypt/blob/master/common/src/main/java/org/conscrypt/CryptoUpcalls.java) routes opaque RSA signing through private-key `Cipher.ENCRYPT_MODE` with PKCS1 or NoPadding. [Native RsaMethodSignRaw](https://github.com/google/conscrypt/blob/master/common/src/jni/main/cpp/conscrypt/native_crypto.cc) accepts those two modes. [AOSP AndroidKeyStoreRSACipherSpi](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/keystore/java/android/security/keystore2/AndroidKeyStoreRSACipherSpi.java):48–57,98–108 maps those private-key operations to signing purpose, mapping PKCS1 to signing padding. This explains the additional raw-padding authorization while retaining SIGN-only purpose. These upstream `main/master` sources explain a compatibility candidate; they are not the exact installed Googlebook provider binary or a completed handshake proof. Use public JCA only, not these private implementation classes.

An authentication-bound generated key can have an invalid initial certificate signature. [KeyGenParameterSpec](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec) explicitly warns that a valid generated self-signature requires unauthenticated signing authorization, among other conditions. Do not disable authentication just to obtain a certificate. Instead, after successful local authorization, create a real self-signed X.509 certificate for the same RSA public key using the already selected BC certificate-building APIs and provider-neutral JCA SHA256withRSA signing. Verify certificate validity, its self-signature and public-key match before committing enrollment. Use a positive random serial, a non-personal subject and explicit finite validity. No attestation challenge or hardware-identifying extension is needed for GameStream pairing.

`JcaContentSignerBuilder("SHA256withRSA").build(privateKey)` is the candidate signer without `.setProvider(bcProvider)`; its [official source](https://github.com/bcgit/bc-java/blob/main/pkix/src/main/java/org/bouncycastle/operator/jcajce/JcaContentSignerBuilder.java) creates a JCA Signature and calls `initSign` on the supplied key. Check the actually resolved BC version during implementation. Android's [cryptography guidance](https://developer.android.com/privacy-and-security/cryptography) and Keystore signing example support provider-neutral operation selection after explicitly selecting AndroidKeyStore for generation. A BC-only signer requiring private RSA parameters is unsuitable.

Persist the verified **public** certificate and versioned alias metadata atomically in credential-encrypted app-private no-backup storage. The provider can return that certificate directly; it need not replace Keystore's initial certificate to satisfy this upstream key manager. Retain its exact bytes and check its public key against the alias on reload. Do not persist a new enrolled record until key/certificate validation succeeds. Missing key, invalid certificate, interrupted generation or mismatched metadata is an unavailable identity requiring deliberate enrollment/repair, with no silent software-key fallback or automatic re-pair.

Use `KeyFactory.getInstance("RSA", "AndroidKeyStore").getKeySpec(key, KeyInfo.class)` and [KeyInfo.getSecurityLevel](https://developer.android.com/reference/android/security/keystore/KeyInfo#getSecurityLevel()) (API31) to report actual backing. TEE/StrongBox/software must be distinguished. StrongBox is not mandatory by inference; an explicit hardware-only policy must fail honestly if unavailable. Do not claim attestation from this local report.

## Authorization, ownership and cancellation gap

The proposed 30-second authorization window follows the existing security contract; it is not a new stream-vault completion claim. Require a secure lock and fresh foreground approval for each new attempt, using the reviewed [BiometricPrompt time-based authentication route](https://developer.android.com/identity/sign-in/biometric-auth), before constructing `NvHTTP`/`PairingManager`, since the latter immediately requests the private key. No per-operation CryptoObject can transparently cover the several independent pairing and TLS signatures created upstream.

A provider alone is insufficient to enforce the whole attempt lifecycle: PairingManager caches the returned private handle, and TLS may sign again on a later connection. The user can take more than 30 seconds entering the server PIN; a handshake may occur after expiry. Do not extend the window silently, auto-retry signing, remove authentication, prompt from a TLS callback thread or treat `UserNotAuthenticatedException` as permission to generate another identity. The adapter needs an explicit authorization-required stage: pause safely before the pairing client-secret signature and before opening a fresh authenticated HTTPS operation, request foreground re-authentication when needed, then resume only the same live attempt. A race with expiry can still fail; expose a bounded authentication-required result and require deliberate retry under a new valid authorization. A working full-stream session may later require a reviewed policy for re-authentication of subsequent HTTPS operations; it is unresolved by this source review.

Use one serialized owner and an attempt-generation token. Getters return only the prepared identity for a live authorized owner, fail closed on stale/cancelled use, and never start prompts or regenerate keys. Guard continuation after every blocking HTTP/authentication phase. Add a narrow HTTP call-registration/cancel hook and finite overall pairing deadline around the actual OkHttp Call; cancel and close response bodies on stop. Cancellation is distinct from the server `unpair` operation: do not revoke an existing enrollment merely because a local attempt is cancelled. Retire the old HTTP/start owner before admitting a replacement; native stop does not establish that retirement.

This app gate cannot cryptographically revoke a private handle already used by an in-flight operation during the system authorization window. Cancel network/continuations and drop owner references; retain that threat limit. Device lock, explicit lock and last-window background follow the reviewed disconnect/no-auto-reconnect policy. Missing/permanently invalidated keys preserve non-secret profiles but require explicit re-enrollment. Pairing identity deletion and host-side revocation are separate operations.

## Backup and finite qualification gate

Public certificates are not private key material, but identity, server pins and enrollment metadata still belong to the owning app. Store them via [Context.getNoBackupFilesDir](https://developer.android.com/reference/android/content/Context#getNoBackupFilesDir()) (API21), declare backup/data-transfer exclusions and keep restoration fail-closed when the key is absent. Android's [backup guidance](https://developer.android.com/identity/data/autobackup) requires attention to manufacturer-dependent device-transfer behavior despite `allowBackup=false`. Never export keys or borrow another app's enrollment to make restored profiles work. Logs/receipts omit PINs, certificate bodies, signed secrets, host/account identities and private key objects.
