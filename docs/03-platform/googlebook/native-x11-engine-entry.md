# Native X11 engine adoption entry

**Checked 2026-10-15. Status: bounded official-source review; engine adoption, compilation and runtime qualification pending.** This entry supports [P0-S7](../../05-delivery/phases/p0-qualification.md#p0-s7--x11-forwarding-and-native-application-window-feasibility) and the [separate application-window contract](../../02-architecture/x11-windows.md). Console must remain independently useful with ordinary SSH. Desktop and a custom host agent are not prerequisites. A single X desktop in one Android window does not satisfy the per-application window requirement.

The strongest reviewed Android engine candidate is [Termux:X11](https://github.com/termux/termux-x11), pinned for this investigation to **`fa3a8b430e2896a19f44c99a9cb056254615ae06`**. Its X.Org submodule is **`65d790bd208ec380b196eb98f144abb0b32e334d`**. This is a source candidate, not an accepted binary dependency or a Googlebook qualification. Termux:X11 is a technical component reference; Termius remains the selected SSH/SFTP product and interaction reference.

The current [pinned README, lines 89–99](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/README.md#L89-L99) documents `-tag` to give separate X displays separate Android windows. Reusing a tag brings its window forward. This is useful for distinct display/trust contexts, but it maps **one X display workspace to one Android window**, not each application XID from a shared display into its own Android top-level window. Starting two displays therefore cannot, by itself, pass the two-application/owned-dialog gate.

## Reusable source and the missing bridge

The actual native build entry is [`add_library(Xlorie SHARED ...)`](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/cpp/recipes/xserver.cmake#L273-L300), producing `libXlorie.so`. It combines the existing X.Org protocol/framebuffer/input core with Android DDX, buffer, renderer and control code. Composite and Damage are already compiled. [The CMake entry](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/cpp/CMakeLists.txt) uses C11/C++17, Android NDK, Python and Bison with pinned submodules. [The library Gradle file](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/build.gradle) sets minSdk24 and compileSdk34. Compatibility with Cloudy's reviewed Googlebook toolchain remains an actual build task; upstream settings are not an instruction to change that toolchain.

The inspected composition path is explicit: [`InitOutput.c:516`](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/cpp/lorie/InitOutput.c#L516) obtains `GetWindowPixmap(pScreenPtr->root)`, while [`renderer.cpp:904`](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/cpp/lorie/renderer.cpp#L904) selects `state->rootWindowTextureID`. The DDX already wraps `SetWindowPixmap`, but the reviewed Android presentation consumes the root composition. An XID-indexed surface/buffer and window-lifecycle bridge is missing from the inspected route. That conclusion does not establish that every upstream feature has been exhaustively audited.

The public Android rendering seam is [`LorieView`'s `SurfaceHolder.Callback`](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/java/com/termux/x11/LorieView.java#L284-L304), which passes a `Surface`, or null on destruction, through native `surfaceChanged(long, Surface)`. The native renderer uses `ANativeWindow_fromSurface` and EGL. This is a plausible handoff to a Cloudy-owned Activity/SurfaceView adapter, not an existing per-XID API or a qualified zero-copy path.

The upstream shell startup must be excluded from the public-API candidate. [`CmdEntryPoint.createContext()`](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/java/com/termux/x11/CmdEntryPoint.java#L150-L174) uses `sun.misc.Unsafe`, `ActivityThread` and hidden framework context creation. Cloudy needs APK-owned process/service startup and a narrow JNI/control adapter using public APIs. Termux's shell loader, shared signing identity, shared UID, root, SELinux changes and hidden framework calls cannot be prerequisites. Existing upstream lifecycle/input/clipboard behavior needs selective adoption rather than importing its phone-oriented shell/UI assumptions wholesale.

The alternative [XServer XSDL upstream](https://github.com/pelya/xserver-xsdl) documents an X screen-buffer copy into an SDL screen/OpenGL texture, a patched SDL build, no XRANDR and problematic text input. No ready per-XID Android surface bridge was established there in this bounded review. It does not currently remove the consequential missing bridge, so a second full build investigation is not justified before testing the stronger candidate's seam.

## SSH transport, authentication and ownership

The engine control connection must not be confused with an X11 client transport. Upstream [`getXConnection()`](https://github.com/termux/termux-x11/blob/fa3a8b430e2896a19f44c99a9cb056254615ae06/lorie/src/main/cpp/lorie/cmdentrypoint.cpp#L550-L563) creates a socketpair registered with `handleLorieEvents`; this is the Lorie activity/control protocol. SSH `x11` channels must enter an actual authenticated X server client connection, not this control descriptor.

Use the ordinary SSH [`x11-req` and incoming `x11` channel protocol, RFC4254 §6.3](https://www.rfc-editor.org/rfc/rfc4254.html#section-6.3), with the selected SSH engine's actual cookie substitution. The remote SSH server needs X11 forwarding permission, usable `xauth` and application dependencies; [`sshd_config`](https://man.openbsd.org/sshd_config) defines `X11Forwarding`, `X11UseLocalhost` and `XAuthLocation`. The local engine needs an authenticated, privately scoped X client entry with no public listener. Neither `-ac`, wildcard `xhost`, a guessed local IP, nor a custom host agent is an acceptable shortcut.

Maintain one isolated display/server ownership domain per incompatible remote trust context. Bind windows and callbacks to `{app session, SSH connection generation, display, XID, window generation}`; XIDs are reusable. Close/recreate/destroy operations must retire stale buffers and callbacks before reuse. An Activity surface can disappear while the local X server remains alive; process death or X connection loss may terminate remote GUI clients. Do not promise tmux-style GUI persistence or automatically rerun remote application commands.

X11 SECURITY/restricted forwarding support has not been established in the exact candidate build. The compiled presence of authentication-related source is not proof of SECURITY enforcement. Qualify extension availability and negative cases before offering restricted mode. If unavailable, report it unavailable and retain only a deliberately selected trusted context with explicit scope; never silently upgrade trust. [OpenSSH's forwarding policy](https://man.openbsd.org/ssh_config) explains the trusted/untrusted distinction.

## Smallest next real proof

1. Prepare exact engine/submodule archives, upstream patches and notices in ignored storage. Compile/load a private diagnostic with a public APK/JNI owner and bounded lifetime. Do not import hidden shell startup or add a global daemon. Record the actual ABI, toolchain, exports, source hashes and result.
2. Build a minimal two-dimensional window broker against existing X.Org/Composite machinery. Observe map/unmap/destroy/configure events and obtain redirected top-level pixmaps for **two actual application XIDs from one display**. Present them into two independently focusable native Activities/tasks using real SurfaceView surfaces. Bounded copying is acceptable for the first measured proof; performance and GPU/zero-copy claims remain separate.
3. Demonstrate independent configure/resize, focus and `WM_DELETE_WINDOW`, then one `WM_TRANSIENT_FOR` dialog and one override-redirect menu. Root-image cropping is inadequate when windows overlap or become occluded. Use [ICCCM](https://xorg.freedesktop.org/archive/X11R7.7/doc/xorg-docs/icccm/icccm.html) for the actual client/window-manager conventions, with system captions and Android ownership/lifecycle preserved.
4. Route physical keyboard, IME and pointer events through explicit focused-window ownership and local-to-X coordinates. Existing screen-global coordinate input cannot be assumed correct for the new per-window mapping. Disable clipboard synchronization initially; treat clipboard/XDND as separate capabilities.
5. Connect through ordinary SSH and real remote `xauth`. Check actual cookie substitution, wrong-cookie rejection, two isolated host contexts, disconnected SSH, stale XID/generation, Activity surface recreation and local process death. Report surviving/ended/unknown clients accurately. Start with a simple X test application and owned dialog; an engineering GUI and broader capability matrix follow only after this missing bridge is real.

The finite stop condition is a recorded two-XID/two-native-window result with correct owned dialog and real SSH/cookie isolation, or a concrete blocker at one of those boundaries. A two-display demonstration, one large X desktop or a successful native compile is useful partial evidence but cannot pass CAP-X11. No new X server implementation or broad protocol reimplementation is proposed.
