# P0-S2 — Operation lifetimes and background execution

**Checked:** 2026-10-15. **Owner:** Android/platform developer. **Status:** reviewed P0-S2 operation decisions with a [bounded platform follow-up](p0-s2-platform-decision.md). A real UIDT `JobService` has finite HTTPS evidence; the [0.8.0 finite SSH retention candidate](p0-s3-ssh-retention-contract.md) now implements and compiles a provisional specialUse route. Its [finite three-case device run](../../../qualification/results/P0-S3/2026-10-15-ssh-retention-cases.md) now qualifies the observed hide/return, notification cancellation and explicit process-loss recovery scope. Indefinite lifetime and distribution approval remain unqualified. API14 has partial runtime evidence; API13 timeout behavior remains untested. CAP-PLATFORM is `experiment`, not supported.

Apply [Rule 0](../../00-project/platform-rule-zero.md), the [desktop contract](desktop-application-contract.md), and [security/lifecycle architecture](../../02-architecture/security-and-lifecycle.md). Console and Desktop own their operations independently. Sharing source does not introduce shared credentials, a cross-app daemon, or a guarantee that a process stays alive. Target SDK 37 does not remove earlier Android execution restrictions.

## Observed last-window limit

The [0.3.0 engagement run](../../../qualification/results/P0-S2/2026-10-15-engagement-probe.md) closed the first window while another stayed alive and recorded successful listener removal. Closing the last remaining window instead left the saved report at its earlier revision; six bounded exports did not establish final cleanup, the process was absent, and the shell exit history reported reason 10 (`USER REQUESTED`) / subreason 22 (`REMOVE TASK`). The public `ApplicationExitInfo.REASON_USER_REQUESTED` constant is available from API 30; its meaning includes user-directed task removal. The shell subreason is an observation, not a public application API. [G78](https://developer.android.com/reference/android/app/ApplicationExitInfo)

This is one task-removal observation on the identified HP build, distinct from the earlier background-process-kill experiment. It does not establish FGS/UIDT behavior, force-stop equivalence, or a guaranteed kill policy for every app. It reinforces the proposed requirement to commit operation state during work and treat missing cleanup acknowledgments as unknown. The diagnostic recorder intentionally cannot guarantee a final queued write after process termination.

## Prerequisite for a real LAN operation

For the selected runtime **37 / target 37** probe, direct LAN access requires `INTERNET` plus the Android 17 dangerous permission `Manifest.permission.ACCESS_LOCAL_NETWORK`. Check the grant with `Context.checkSelfPermission`, request through `Activity.requestPermissions` for the actual user operation, and handle denial/revocation explicitly. API41's constant/value is present in the selected SDK37.0 `android.jar`. The [0.4.0 preflight](../../../qualification/results/P0-S2/2026-10-15-transfer-preflight.md) observed actual permission denial/grant and blocked app admission while denied. The [0.4.1 run](../../../qualification/results/P0-S2/2026-10-15-transfer-lifecycle.md) then completed HTTPS through the OS-assigned network after grant. Its existing VPN route does not qualify direct-LAN enforcement; no denied-socket or revocation result is claimed. Earlier permission-free APK evidence retains its original version. [G79](https://developer.android.com/privacy-and-security/local-network-permission), [G80](https://developer.android.com/about/versions/17/behavior-changes-17), [G81](https://developer.android.com/reference/android/Manifest.permission.html#ACCESS_LOCAL_NETWORK)

Keep this prerequisite under **API41 / P0-S2**. Local TCP denial may look like a timeout; do not blame the host or routing before checking app access. The permission reference defines LAN over Wi-Fi/Ethernet separately from cellular/VPN, so shell ICMP and a VPN route are independent observations. Do not add unrelated Nearby Devices permissions to obtain a group grant. System-mediated mDNS service selection is an alternative requiring its own discovery/connection experiment, not a tested replacement for the fixed-host route. No permission grant implies SSH authentication, TLS trust, server readiness or UIDT scheduling eligibility.

## Visibility and native ownership

Use per-window visibility and actual input focus as separate signals. On API29+, multiple activities may remain resumed; losing focus does not mean a window became hidden. Retain visible rendering while another window has focus, but release that window's captured pointer/held input according to the backend contract. `onStop()` is the visibility boundary to evaluate hidden video, not `onPause()` alone. `onTopResumedActivityChanged()` is an exclusive-resource signal, not a transport-liveness guarantee. [G99 multi-window lifecycle](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode)

A process-owned executor or bound coordinator does not create background execution entitlement. Ordinary asynchronous work serves the visible protocol experiment; moving work off the UI thread does not ensure completion after visibility is lost. Cached processes can receive little or no execution time and can die without `onDestroy()`. Persist during work, rebind on Activity recreation, and reconcile a new process without replay. This is the initial experiment boundary, not a promise that hidden SSH survives. [G98 background-work selection](https://developer.android.com/develop/background-work/background-tasks), [G72 process lifecycle](https://developer.android.com/guide/components/activities/process-lifecycle)

The connected-device guide lists several alternative prerequisites, including network-state permissions and USB permission requests. The `ServiceInfo` reference more precisely requires **granted access** to an attached USB device/accessory for the USB route. A pending or denied request is not access. Network-connected devices are within the documented category, but ordinary `INTERNET` access alone is not one of its listed prerequisites. This leaves generic SSH/background-desktop classification unresolved; it does not justify unrelated network, Bluetooth or ranging permissions. Starting an FGS from the background is restricted for target 31+ on applicable runtimes. Type/runtime-permission checks apply for target 34+, and a background-start exemption need not satisfy while-in-use permission requirements. `remoteMessaging` is messaging continuity, `mediaProjection` captures/projects local content with consent, and `mediaProcessing` processes media assets. ## Timeouts, user stop and audio

For target 35+ on runtime 35+, background `dataSync` and `mediaProcessing` each have a separate six-hour budget per 24 hours, shared by all services of that type within an app. Bringing the app foreground resets the timer. Starting another service does not create another budget. On timeout, stop within the brief grace period; exhaustion can reject a further start. Cloudy's proposed timeout path calls `stopSelf()` rather than depending on demotion. The dedicated guide describes a fatal internal exception if it fails to stop; the type overview uses different failure wording, so record the actual exception/ANR on the qualified build instead of assuming a log signature. [G15](https://developer.android.com/develop/background-work/services/fgs/timeout)

UIDT avoids ordinary job quotas but is still interruptible: constraints, thermal pressure, duration assessment and process loss can stop it. Task Manager stop can kill the entire app without `onStopJob()` and prevent user-visible job rescheduling. Persist transfer checkpoints during execution, not only in shutdown callbacks. Define network constraints for the actual LAN/VPN route; the guide's illustrative Internet/unmetered constraints are not Cloudy's host-access requirement. [UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt)

For ordinary FGS user-stop behavior, Android 13+ Task Manager can terminate the whole app without callbacks; existing scheduled jobs and alarms have separate behavior. Treat this distinctly from UIDT's stop rules, Activity recreation, task removal and force-stop. [User-stop guide](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)

On Android 16+, jobs launched from an FGS remain subject to their own quotas. Wrapping a job in an FGS or WorkManager does not establish unlimited execution. [FGS changes](https://developer.android.com/develop/background-work/services/fgs/changes)

Android 17 restricts background playback, audio focus and volume interactions. All apps on API 37 need a visible Activity or an FGS other than `shortService`; target 37 additionally requires that background FGS to have while-in-use capabilities. User-initiated/visible starts can grant those capabilities; many background-start exemptions do not. Playback/volume calls can fail silently, while focus requests return `AUDIOFOCUS_REQUEST_FAILED`. Qualify actual audible output, not just a successful method call. Cloudy will not obtain alarm permissions or label remote audio as an alarm to bypass this contract. [Android 17 audio guidance](https://developer.android.com/about/versions/17/changes/bg-audio)

## Distribution review and remaining experiments

Google Play requires target 34+ FGS declarations, feature explanations, interruption/deferment impact, and demonstration videos. All types are subject to review, including `specialUse`; a successful debug launch is not policy approval. Document the chosen distribution channel and review outcome separately for each app. A directly installed APK still faces Android OS restrictions. The UIDT probe's permissions and service are recorded in its own reviewed source; the linked 0.8.0 candidate adds its declared specialUse service/permissions with compile evidence, while runtime and distribution approval remain pending. [Play Console requirements](https://support.google.com/googleplay/android-developer/answer/13392821)

The Android/platform owner must retain these route-specific cases under `qualification/results/P0-S2/` or the linked backend investigation. The [CAP-PLATFORM experiment](p0-s2-platform-decision.md) permits P0-S3 investigation while product foundation stages remain gated. These are not all prerequisites to finishing the initial decision record, and an unused service type does not require a dummy implementation. They remain required before support is claimed for their actual operation:

1. **Eligibility:** exercise real starts while visible, after backgrounding and after denial; record the exact service type, prerequisites, notification, target/runtime and rejection. A diagnostic service may qualify OS behavior only; it must not impersonate a product operation.
2. **Timeout:** if a timed `dataSync`/`mediaProcessing` FGS route is selected, exercise normal completion, accelerated timeout and exhausted-budget rejection. No such route was selected or tested by the UIDT experiment. Official `data_sync_fgs_timeout_duration` test configuration is device-wide: capture its prior value, scope the lab change, restore it and verify restoration. Accelerated evidence is not a six-hour endurance pass. UIDT stop/deadline behavior needs its own tests, not an FGS timer substitute. Do not change settings during unrelated probe work.
3. **Transfer loss:** interrupt before publication, during acknowledgement and after remote publication; compare actual destination state and journal recovery. Test graceful cancellation separately from Task Manager stop and abrupt process loss. No blind replacement or duplicate publish.
4. **Lifetime separation:** test Activity recreation with unchanged process identity, then actual process loss with changed identity. Record task/window restoration independently from network reconnection and host process survival. Force-stop has additional package-state semantics and must be labeled explicitly.
5. **Visibility/audio:** test multiple visible windows, unfocused-but-visible, all hidden, lid/sleep and reconnect. Verify backend pause, released input and actual audio behavior. Any global audio-hardening test override requires captured/restored prior state; it cannot stand in for default-policy testing.
6. **USB/provider:** qualify actual grant denial, ownership conflict, detach, re-enumeration and provider/process loss once suitable hardware exists. Until then, software state-machine tests remain test evidence only, with physical claims pending.

The accepted [0.4.1 transfer run](../../../qualification/results/P0-S2/2026-10-15-transfer-lifecycle.md) resolves finite completion, Activity recreation/minimize/return, UI/notification cancellation, wrong-CA rejection, fixture interruption, explicit retry and one injected process-loss recovery within its exact scope. Task Manager, separate active-task removal, wrong hostname, permission revocation, assigned-network change and deadline cases remain pending at this decision. No finite result certifies continuous SSH, streaming, USB or SFTP publication.
