# P0-S2 — Operation lifetimes and background execution

**Checked:** 2026-10-15. **Owner:** Android/platform developer. **Status:** researched proposals for P0-S2 and P1-S3; no service implementation or runtime qualification. API13/API14 and capability gates retain their existing status. The current probe's window observations do not establish background reliability.

Apply [Rule 0](../../00-project/platform-rule-zero.md), the [desktop contract](desktop-application-contract.md), and [security/lifecycle architecture](../../02-architecture/security-and-lifecycle.md). Console and Desktop own their operations independently. Sharing source does not introduce shared credentials, a cross-app daemon, or a guarantee that a process stays alive. Target SDK 37 does not remove earlier Android execution restrictions.

## Proposed operation choices

These are project interpretations of the official contracts below, pending implementation review and real experiments. A permission must serve an actual feature; adding one solely to pass a foreground-service prerequisite is prohibited.

| Operation | Proposed owner and execution route | Fallback and recovery boundary |
| --- | --- | --- |
| Interactive SSH, tunnels and terminal sessions | Console's native coordinator owns live connections while its windows are in use. Continuous background SSH remains a classification decision: evaluate `connectedDevice` only against the actual external-device operation and genuine prerequisites; otherwise evaluate a justified `specialUse` case. Neither route is selected by this note. | Persist profiles/view state, expose disconnection, and reconnect through host verification. Host-side tmux can preserve eligible remote processes; it does not preserve a client socket. Never replay terminal input or remote commands. If no valid background route is established, explicitly bound background availability. |
| User-requested SFTP upload/download, including drop | Prefer evaluating Android 14+ user-initiated data transfer jobs (UIDT) for long network transfers started by the user. Keep the [transfer journal](../../02-architecture/console-files.md) independent of the Activity. A `dataSync` foreground service is an alternative requiring its own bounded-duration decision; it is not a permanent session keeper. | Queue or pause when launch/constraints fail; resume only after validating source, destination and partial state. Preserve unpublished bytes. Apply [publication recovery](../../02-architecture/file-publication.md): an interrupted commit is completion-unknown, and nonconditional replacement requires the user's per-save overwrite consent. |
| Local USB forwarding owned by Cloudy | Evaluate `connectedDevice` only while the app actually owns authorized access and performs the enrolled operation. The Android USB grant and remote consumer ownership are different checks. Show active forwarding and a usable detach control. | On denial, detach, reset or process loss, reconcile actual provider and consumer state. Retain intended enrollment, not a fabricated attached state. No automatic programming retry or ownership theft. The user's unspecified board/probe leaves physical compatibility pending, while generic software/provider scope remains intact. |
| External USB provider or streaming app | The separately installed provider owns its device/service lifecycle. Cloudy may inspect or control it only through a documented, qualified interface. | Provider unavailable/unknown is a real state. Cloudy's own foreground service cannot establish the other app's permission, survival or ownership. |
| Native streaming, RDP and VNC | Desktop's native backend owns the connection; windows own surfaces/input. Default to rendering and audio while visible, releasing pointer capture/held modifiers on focus loss and stopping hidden video at the backend. Background connection retention requires a separate justified classification, as with SSH. | Reconnect using each backend's actual session model. Release stale local resources, display disconnected/unknown status, and do not equate a surviving host desktop with a surviving client transport. |
| Optional continued remote audio | If a user-visible feature explicitly continues real audio playback while hidden, separately evaluate `mediaPlayback`, its notification and Android 17 while-in-use requirements. This is not justification for retaining unrelated SSH, USB or silent desktop work. | Stop audio when the lifecycle cannot support it; show a visible resume action. The current scope has no background-audio qualification. |
| Separate X11 windows | Keep the local X server/broker independent of the shell Activity while a valid owner exists. Background-service eligibility remains part of Console's classification work. | Activity recreation may rebind a live broker. Process/X-connection loss can terminate GUI clients; tmux offers no X11 survival guarantee. Follow [X11 lifetime rules](../../02-architecture/x11-windows.md). |

## Android contracts and guards

Any selected FGS must declare `FOREGROUND_SERVICE`, the appropriate `android:foregroundServiceType`, and its required type permission (for example `FOREGROUND_SERVICE_CONNECTED_DEVICE` or `FOREGROUND_SERVICE_DATA_SYNC` for target 34+). Select only the types needed by the actual operation. [FGS requirements by version](https://developer.android.com/develop/background-work/services/fgs/changes)

| Contract and exact entry point | Availability / target guard | Proposed use or fallback |
| --- | --- | --- |
| `ServiceInfo.FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE` and `FOREGROUND_SERVICE_TYPE_DATA_SYNC` | Constants added API 29. For target 34+, apply the type-specific permissions and prerequisites on relevant runtimes. | Candidate USB ownership and bounded transfer routes, respectively. No type is selected merely because bytes cross a socket. [ServiceInfo reference](https://developer.android.com/reference/android/content/pm/ServiceInfo) |
| `ServiceInfo.FOREGROUND_SERVICE_TYPE_SPECIAL_USE` | Added API 34. Requires `FOREGROUND_SERVICE_SPECIAL_USE`; declare `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE`. | Possible continuous-session route only after a concrete justification explains why existing types and job APIs do not fit; retain explicit reconnect fallback. [Type guidance](https://developer.android.com/develop/background-work/services/fgs/service-types) |
| `JobInfo.Builder.setUserInitiated(true)`, `JobScheduler.schedule()` | UIDT available API 34+; declare `RUN_USER_INITIATED_JOBS` and a `JobService` protected by `BIND_JOB_SERVICE`. Schedule while visible or under the specific allowed conditions; inspect scheduling failure. | Candidate long user-requested SFTP transfer. Below API 34, use a separately reviewed supported transfer route or visible-only work; do not silently invent a new minimum OS. [UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt) |
| `JobService.setNotification(JobParameters,int,Notification,int)` | Added API 34; required UIDT notification must be supplied within 10 seconds of `onStartJob()`, on every run. | Use an accurate transfer/progress notification and explicit cancellation. Missing the deadline causes an ANR and job stop. [JobService reference](https://developer.android.com/reference/android/app/job/JobService) |
| `Service.onTimeout(int,int)` | Added API 35; runtime 35+ callback. Target 35+ activates the documented background `dataSync` limit. | Cancel work promptly and call `stopSelf()`; journal continuously beforehand. On older supported runtimes, stop explicitly without depending on this callback. [Service reference](https://developer.android.com/reference/android/app/Service), [G15 timeout guidance](https://developer.android.com/develop/background-work/services/fgs/timeout) |
| `UsbManager.hasPermission()`, `requestPermission(UsbDevice,PendingIntent)`, `openDevice()` | USB device APIs added API 12; check `PackageManager.FEATURE_USB_HOST` and actual grant/open result. | Permission is temporary until disconnection. Re-enumeration requires rechecking identity and access. USB video-class access has additional camera-permission requirements for target 28+; do not request camera access for unrelated device classes. [UsbManager reference](https://developer.android.com/reference/android/hardware/usb/UsbManager) |

The connected-device guide lists several alternative prerequisites, including network-state permissions and USB permission requests. The `ServiceInfo` reference more precisely requires **granted access** to an attached USB device/accessory for the USB route. A pending or denied request is not access. Network-connected devices are within the documented category, but ordinary `INTERNET` access alone is not one of its listed prerequisites. This leaves generic SSH/background-desktop classification unresolved; it does not justify unrelated network, Bluetooth or ranging permissions. [G16 service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [connected-device API contract](https://developer.android.com/reference/android/content/pm/ServiceInfo#FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE)

Starting an FGS from the background is restricted for target 31+ on applicable runtimes. Type/runtime-permission checks apply for target 34+, and a background-start exemption need not satisfy while-in-use permission requirements. Start an approved operation through its actual user action while eligible; handle rejection without retry loops or manufactured UI launches. [Background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

`remoteMessaging` is messaging continuity, `mediaProjection` captures/projects local content with consent, and `mediaProcessing` processes media assets. None is selected for an incoming remote desktop or shell. `shortService` has an approximately three-minute lifetime and cannot provide sustained connectivity. [G16 service types](https://developer.android.com/develop/background-work/services/fgs/service-types)

## Timeouts, user stop and audio

For target 35+ on runtime 35+, background `dataSync` and `mediaProcessing` each have a separate six-hour budget per 24 hours, shared by all services of that type within an app. Bringing the app foreground resets the timer. Starting another service does not create another budget. On timeout, stop within the brief grace period; exhaustion can reject a further start. Cloudy's proposed timeout path calls `stopSelf()` rather than depending on demotion. The dedicated guide describes a fatal internal exception if it fails to stop; the type overview uses different failure wording, so record the actual exception/ANR on the qualified build instead of assuming a log signature. [G15](https://developer.android.com/develop/background-work/services/fgs/timeout)

UIDT avoids ordinary job quotas but is still interruptible: constraints, thermal pressure, duration assessment and process loss can stop it. Task Manager stop can kill the entire app without `onStopJob()` and prevent user-visible job rescheduling. Persist transfer checkpoints during execution, not only in shutdown callbacks. Define network constraints for the actual LAN/VPN route; the guide's illustrative Internet/unmetered constraints are not Cloudy's host-access requirement. [UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt)

For ordinary FGS user-stop behavior, Android 13+ Task Manager can terminate the whole app without callbacks; existing scheduled jobs and alarms have separate behavior. Treat this distinctly from UIDT's stop rules, Activity recreation, task removal and force-stop. [User-stop guide](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)

On Android 16+, jobs launched from an FGS remain subject to their own quotas. Wrapping a job in an FGS or WorkManager does not establish unlimited execution. [FGS changes](https://developer.android.com/develop/background-work/services/fgs/changes)

Android 17 restricts background playback, audio focus and volume interactions. All apps on API 37 need a visible Activity or an FGS other than `shortService`; target 37 additionally requires that background FGS to have while-in-use capabilities. User-initiated/visible starts can grant those capabilities; many background-start exemptions do not. Playback/volume calls can fail silently, while focus requests return `AUDIOFOCUS_REQUEST_FAILED`. Qualify actual audible output, not just a successful method call. Cloudy will not obtain alarm permissions or label remote audio as an alarm to bypass this contract. [Android 17 audio guidance](https://developer.android.com/about/versions/17/changes/bg-audio)

## Distribution review and remaining experiments

Google Play requires target 34+ FGS declarations, feature explanations, interruption/deferment impact, and demonstration videos. All types are subject to review, including `specialUse`; a successful debug launch is not policy approval. Document the chosen distribution channel and review outcome separately for each app. A directly installed APK still faces Android OS restrictions. No permissions, manifests, distribution decision or API qualification status changes follow from this research note. [Play Console requirements](https://support.google.com/googleplay/android-developer/answer/13392821)

The Android/platform owner must record these cases under `qualification/results/P0-S2/` and carry backend-specific cases into P0-S3/S4/S5/S7 and P1-S3:

1. **Eligibility:** exercise real starts while visible, after backgrounding and after denial; record the exact service type, prerequisites, notification, target/runtime and rejection. A diagnostic service may qualify OS behavior only; it must not impersonate a product operation.
2. **Timeout:** when a real bounded transfer route exists, exercise normal completion, accelerated timeout and exhausted-budget rejection. Official `data_sync_fgs_timeout_duration` test configuration is device-wide: capture its prior value, scope the lab change, restore it and verify restoration. Accelerated evidence is not a six-hour endurance pass. Do not change settings during unrelated probe work.
3. **Transfer loss:** interrupt before publication, during acknowledgement and after remote publication; compare actual destination state and journal recovery. Test graceful cancellation separately from Task Manager stop and abrupt process loss. No blind replacement or duplicate publish.
4. **Lifetime separation:** test Activity recreation with unchanged process identity, then actual process loss with changed identity. Record task/window restoration independently from network reconnection and host process survival. Force-stop has additional package-state semantics and must be labeled explicitly.
5. **Visibility/audio:** test multiple visible windows, unfocused-but-visible, all hidden, lid/sleep and reconnect. Verify backend pause, released input and actual audio behavior. Any global audio-hardening test override requires captured/restored prior state; it cannot stand in for default-policy testing.
6. **USB/provider:** qualify actual grant denial, ownership conflict, detach, re-enumeration and provider/process loss once suitable hardware exists. Until then, software state-machine tests remain test evidence only, with physical claims pending.
