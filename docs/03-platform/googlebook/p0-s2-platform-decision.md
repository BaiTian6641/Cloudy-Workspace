## Bounded follow-up: real SSH ownership and classification

**Hypothesis:** one reviewed native SSH engine can own a real ordinary-SSH session independently of its renderer and Activity generation on the selected Linux host, while a separately justified service route can make any requested hidden-session lifetime explicit. Window focus, visibility, transport ownership and persisted recovery must remain distinct. This is an experiment, not an assumption that a generic SSH connection qualifies for a service type.

**Owner:** Android/platform developer with Terminal/Android developer. **Effort cap:** two engineer-days for this first platform follow-up within P0-S3; this is a bounded investigation allowance, not a product estimate or a claim that all remaining platform tests fit within it. Review the verdict before any extension.

1. Review/pin the SSH candidate and its Android build, license, trust/authentication and SFTP interfaces. Prepare one scoped ordinary-SSH fixture on the selected Linux host, with independently checked server identity. No custom host agent, terminal bridge or streaming engine is required for the first transport experiment.
2. Implement real native connection ownership with bounded counters/events and explicit Connect/Disconnect. Prove first-trust cancellation/changed-key rejection, authentication and a small actual SFTP hash round trip independently of rendering. Window recreation must rebind to the same live owner where intended; a second visible window must not silently steal it. Keep secrets/transcripts out of public evidence.
3. Before any hidden-session service is implemented, review the actual feature against API14. `connectedDevice` needs an applicable external-device operation and genuine prerequisite. If no specific type fits, assess `specialUse` with an exact subtype justification, visible user start, accurate ongoing notification and stop action. The [finite SSH retention contract](p0-s3-ssh-retention-contract.md) now justifies a provisional specialUse experiment and has compile evidence. Product classification and distribution remain unapproved. A synthetic keepalive or unrelated permission cannot resolve classification. Debug OS behavior and distribution approval require separate verdicts.
4. For an accepted candidate only, test visible/unfocused-visible, Activity recreation, all windows hidden/return, explicit UI/notification stop, and one scoped process-loss/reconciliation case. Record actual transport continuity/closure, process and owner generations, event ordering, and absence of command replay. If no type can be justified, record that result and continue only the visible transport/renderer investigation; full background scope stays unmet.

**Stop condition:** stop the candidate on an unsupported API/type/prerequisite, required private API or unrelated permission, lost ownership, unexpected authentication/replay, unbounded resources or the two-day cap. Preserve failures and report blocked/inconclusive scope; do not restart under another label or extend the cap silently.

**Expected evidence:** exact source/APK/engine/server/build/route identities; independent code review and compiler/lint/tests; actual SSH/SFTP trust and byte evidence; window/owner/process correlation; candidate declaration/prerequisites and real notification/stop observations or documented classification blocker; recovery without input replay; a separate distribution assessment. The P0-S3 matrix must also retain **physical keyboard, trackpad/mouse, native IME/preedit and exact committed bytes, focus-loss modifier/pointer release, keyboard navigation and accessibility** as required evidence. Injected ADB events, engagement hints and synthetic tests cannot satisfy those physical cases. Missing physical interaction is recorded as pending, not waived by successful transport.

## Remaining required work and readiness boundary

- **CAP-PLATFORM:** continuous-session classification, real input/focus-release behavior, complete applicable Q-P02 geometry/display cases and backend-specific lifetime behavior remain unresolved. CAP-PLATFORM cannot become supported solely from another successful finite download or this decision.
- **API39/API41 finite transfer:** Task Manager stop, separate task removal during active work, wrong-hostname rejection, LAN permission revocation/denied-socket enforcement, assigned-network change and deadline/stop paths remain pending at this closeout. A VPN route does not qualify direct-LAN permission enforcement. New experiments may resolve individual entries only after review.
- **Conditional routes:** FGS timeout/exhausted-budget tests are required if a timed FGS is actually selected. Background audio, USB/provider loss, hidden video, sleep/lid and protocol reconnect tests belong to their real backends. They are not replaced by a dummy universal service or an exhaustive test of every unused Android service type.
- **Product gates:** P0-S3 investigation may proceed because P0-S2's investigation decision is complete. CAP-SSH/CAP-TERMINAL remain pending and require separate evidence/adoption. P1-S1/S2/S3 and all dependent product work remain subject to their existing supported-capability gates. Full separate X11 windows, SFTP/drop, native RDP/VNC and enrolled USB plug-and-play remain requested requirements.

The official [background-work selection guidance](https://developer.android.com/develop/background-work/background-tasks) distinguishes visible asynchronous work, scheduled finite work and foreground services. [Multi-window guidance](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode) distinguishes visibility from focus and supports multiple resumed activities. [Process lifecycle guidance](https://developer.android.com/guide/components/activities/process-lifecycle) does not guarantee cached-process execution or final callbacks. These are the reasons for the bounded ownership experiment; none grants a Googlebook-specific exemption from Android lifetimes.
