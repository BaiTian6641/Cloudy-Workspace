## Operation and classification

The experiment retains one explicitly requested, finite SSH exec+PTY operation when its last Activity observer hides. It uses the existing application-owned `ProbeApplication.ssh` / `SshRuntime` and real `SshEngine.runExecPty` path: authenticated SSH, the existing fixed exec exchange, then the existing controlled PTY protocol and explicit controls. It adds no dummy heartbeat, terminal renderer, tunnel or custom host-agent dependency. The separate real `TerminalRuntime` is unchanged. The finite transfer scheduler cannot represent interactive PTY ownership, and ordinary INTERNET/LAN access does not satisfy the documented connected-device prerequisites. No unrelated permission is added to manufacture eligibility.

`SshOperation.RETAINED_EXEC_PTY` has an application cancellation deadline of 180 seconds. The existing PTY channel-read timeout is **120 seconds**. The outer deadline does not extend that read timeout or promise 180 seconds of successful operation. The 10-second bound belongs to the pending start ticket described below.

The provisional foreground-service type is `specialUse`, for a user-started finite remote-session ownership experiment whose purpose is maintaining an interactive SSH operation across UI hiding. It is not justified as `dataSync` merely because SSH carries bytes. Declare `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, the service type and a truthful `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explanation. This is a candidate classification requiring actual platform behavior and distribution review, not an approved general background-SSH category. [G16: foreground-service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [G64: ServiceInfo](https://developer.android.com/reference/android/content/pm/ServiceInfo).

The parent accessed G16 through the official Android CLI knowledge-base route `kb://android/develop/background-work/services/fgs/service-types`, retained privately at `.cache/ssh-retention-01/official-types.md`; the direct web fetch timed out. ## Admission, ownership and retirement

`SshSessionService.requestStart(Activity, visiblePredicate): Boolean` runs on the main thread. True means one pending request was accepted; it does not mean service promotion, connection, authentication or retention succeeded. A visible, nonfinishing Activity reserves a one-use UUID ticket with a 10-second monotonic expiry. Explicit service delivery must match that exact ticket. The service performs actual foreground promotion **before** consuming the ticket or entering network work. Expired, duplicate, cancelled and mismatched starts cannot create another engine or reset a cancelled attempt. Launch/promotion failure retires the exact reservation without connecting. [G60: background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [G155: launch and promotion](https://developer.android.com/develop/background-work/services/fgs/launch).

A service observer is separate from the bounded UI-window observer set. Ordinary operations retain last-visible-window-hide cancellation. Only an explicit retained operation with acquired service ownership continues across hiding. Returning attaches an observer to that same operation; it does not start another authentication or connection. Cancellation stays sticky before engine installation and is rechecked afterward. The service must not retain an Activity merely to satisfy a visibility predicate.

This diagnostic chooses granted `POST_NOTIFICATIONS`, enabled notifications and an enabled notification channel as admission prerequisites so its user has a visible stop route. **Notification permission is not an OS prerequisite for starting a foreground service**; the stricter condition is this probe's chosen control contract. Denial must expose unavailability rather than silently start. [G22: notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

Notification stop actions and pending intents identify the exact attempt; a stale action cannot cancel a later attempt. `START_NOT_STICKY`, explicit one-use admission and no replay/reconnect apply together: nonsticky return alone is insufficient protection against stale explicit intents. Service cancellation closes admission and requests real engine cancellation. Notification removal or a cancellation callback is not proof of actual retirement. Keep ownership until worker/helper retirement and terminal journal persistence/readback are established. Existing helper/client-cleanup uncertainty and journal failure remain quarantined; do not clear the busy slot or fabricate a clean record to admit another operation. Process loss is recovered as interrupted evidence on a later explicit launch, with no automatic network restart. [G62: user stopping](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping), [G67: Service callbacks](https://developer.android.com/reference/android/app/Service). A defensive timeout callback does not imply that `specialUse` has a timed-type budget.

## Finite qualification and evidence tiers

The next device packet uses at most three retained attempts after confirming capacity and preserving every historical row. Follow the existing [SSH batch archive/restore contract](p0-s3-journal-batch-handoff.md) if rotation is needed; do not run an old hardcoded helper against a new batch or erase history without its verified restoration drill.

1. **Hide/return:** reach actual PTY readiness, hide the last UI observer, observe finite continuation, then return without Start. Correlate the same attempt/process/engine with host authentication and channel counts; require no second connection. Complete through existing explicit controls.
2. **Notification cancel:** reach readiness, hide, cancel the exact attempt from its notification. Require actual helper disappearance, joined/retired ownership and a durable terminal journal. Reopening must not replay.
3. **Process loss:** reach readiness, perform scoped controlled process loss, preserve unfinished bytes, then explicitly reopen. Require interrupted reconciliation and no automatic authentication, attempt or service restart. Do not label process death as an in-process clean shutdown.

Host and device clocks remain separate. Notification presence, UI clickability and journal labels alone are insufficient. Use existing fixed exec/PTY audits, host authentication/session counts, helper observations and app evidence; do not recreate upstream SSH tests. Tests of changed ticket/ownership/cancellation code should cover stale/duplicate starts, cancellation before engine installation, failed promotion, ordinary versus retained hiding, stale stop actions and cleanup uncertainty.

Source/compiler/unit/Lint/build evidence demonstrates the authored boundaries compile and their tested policies behave. Only actual Googlebook runs establish foreground promotion, retained operation and notification/process behavior. Neither tier grants Google Play approval: `specialUse` subtype justification and foreground-service declarations remain a separate distribution review. [G68: Play declarations](https://support.google.com/googleplay/android-developer/answer/13392821).

The finite experiment does not qualify indefinite sessions, physical keyboard/native IME, window/geometry/accessibility behavior, jump/direct tunnels, X11, a general terminal renderer, product credential storage or a shipping Console. CAP-SSH/CAP-TERMINAL and the platform/product gates retain their existing deciding stages. No result counts or acceptance are inferred from this contract.
