# P0-S4 native desktop engine entry

**Checked:** 2026-10-15, America/Chicago. **Owner:** Desktop/device developer; integration leader accepts the next build. **Status:** reviewed-source candidate brief, no build or device evidence. P0-S2 permits this independent investigation while P0-S3 continues. CAP-RDP and CAP-VNC remain pending. Apply [D12](../../05-delivery/library-reuse-policy.md) and the [desktop backend contract](../../02-architecture/remote-desktop-backends.md).

## Entry decision

Proceed first with an isolated **FreeRDP 3.32.2 arm64-v8a Android library build**, using its maintained Android client/JNI as the integration reference. Keep LibVNCClient as the VNC candidate, but **do not connect unpatched 0.9.15 to a server**: the [accepted source review](../../07-reference/2026-10-15-vnc-patched-source-selection.md) selects exact upstream `98aaee0560baa0332339b2ef464ea96ed9b9b28c`, containing the three identified fixes, with focused runtime regressions and Android build/integration still pending. This is a bounded build-entry recommendation, not library adoption, product implementation or protocol qualification.

Both eventual native engines belong to Desktop's own package/process, credentials and lifecycle. Ordinary RDP/VNC servers need no Cloudy agent or Console installation. A standalone upstream app can help identify an integration fault but cannot satisfy Cloudy's native client gate. No alternative protocol stack implementation is proposed.

Use a cache-local exact checkout and an isolated project-local Gradle home for the first build. Supply explicit `ABI_FILTERS=arm64-v8a`, matching split settings, and version identity through the upstream override mechanism. The existing `freeRDPCore` **qa** build type disables FFmpeg, OpenH264, Opus, WebP, JPEG and PNG, while retaining cJSON/OpenSSL; start with its intent and explicitly set the top-level CMake arguments as well so defaults cannot re-enable optional dependencies. Keep MediaCodec off for the first software-rendering probe. This narrower build establishes core desktop integration only; server-required H.264 may make that server unavailable to this candidate and must be reported rather than silently asserted supported.

The [external-dependency driver](https://github.com/FreeRDP/FreeRDP/blob/3.32.2/client/Android/cmake/ExternalDeps.cmake) and [version/hash file](https://github.com/FreeRDP/FreeRDP/blob/3.32.2/cmake/DepVersions.cmake) pin OpenSSL `openssl-4.0.1`, cJSON `v1.7.19` and uriparser `1.0.2`, with archive SHA-256 values. Uriparser is unconditional. Capture the actual resolved/downloaded graph and check the upstream hashes before execution; these source declarations are not downloaded-artifact verification. Retaining freeRDPCore Java wholesale also brings AndroidX, Room and SQLCipher dependencies; its bookmark database is not required Cloudy architecture. Decide after the build whether to consume a reviewed internal AAR or isolate its JNI/native bridge without importing the upstream profile/storage/UI layer. Avoid a premature fork or a second native binding.

[ExternalFreeRDP.cmake](https://github.com/FreeRDP/FreeRDP/blob/3.32.2/client/Android/cmake/ExternalFreeRDP.cmake) disables server/SDL/sample builds but enables printer and camera channel compilation. Build inclusion does not authorize channel use: first probe requests no camera, microphone, USB, drive/printer or clipboard redirection. Verify the final manifest, runtime argument vector, linked libraries, notices and native dependencies rather than inferring the reduced graph from the qa label.

For LibVNCClient, the [0.9.15 README](https://github.com/LibVNC/libvncserver/blob/LibVNCServer-0.9.15/README.md) documents Android CMake crosscompilation; [CMakeLists.txt](https://github.com/LibVNC/libvncserver/blob/LibVNCServer-0.9.15/CMakeLists.txt) defines the actual `vncclient` target. Use the same qualified NDK and API/ABI inputs when this lane opens. Set `CMAKE_TOOLCHAIN_FILE` to the NDK's `build/cmake/android.toolchain.cmake`, `ANDROID_ABI=arm64-v8a`, `ANDROID_PLATFORM=android-29`; keep each ABI in a separate build directory. Disable examples/tests and unneeded desktop integrations (`WITH_SDL`, `WITH_GTK`, `WITH_QT`, `WITH_XCB`, `WITH_SYSTEMD`, `WITH_FFMPEG`, `WITH_LIBSSHTUNNEL`) and build/package only `vncclient`, not a VNC server. Decide exact TLS/compression dependency pins before build; Android does not supply an NDK OpenSSL API. No executable CMake recipe is claimed tested.

Google's [NDK CMake guide](https://developer.android.com/ndk/guides/cmake) documents the toolchain, ABI and platform arguments; [side-by-side installation guide](https://developer.android.com/studio/projects/install-ndk) supports explicit tool versions. Neither page certifies this particular upstream build. Product minSdk and ABI policy remain a later decision.

## License and security gates

FreeRDP's [tagged root license](https://github.com/FreeRDP/FreeRDP/blob/3.32.2/LICENSE) is Apache-2.0. Review its actual enabled dependency graph, notices and any modifications before embedding/distribution under P1-S4. The smaller first build avoids optional FFmpeg/OpenH264 scope but does not settle other dependencies, codec patent questions or Cloudy's own license. Preserve a single update owner and official [security-advisory route](https://github.com/FreeRDP/FreeRDP/security/advisories). The 3.32.2 release includes numerous fixes; no comprehensive upstream audit is requested.

LibVNCClient's tagged header carries GPL-2.0-or-later terms; the README explicitly describes linking consequences for distributed programs. Cloudy currently has no selected blanket project license. A private isolated investigation does not decide a distributable integrated product license; P1-S4 must resolve the intended distribution/source obligations before embedding the client in a product. An external viewer is only a partial fallback and does not meet the required native VNC lane.

The official [LibVNC security policy](https://github.com/LibVNC/libvncserver/security) says security fixes go to master and downstreams should cherry-pick; old releases get no point releases. Review these consequential client advisories before opening its network probe:

- [GHSA-v9pm-47h4-jcq8](https://github.com/LibVNC/libvncserver/security/advisories/GHSA-v9pm-47h4-jcq8): Tight decoder out-of-bounds write; advisory range starts at 0.9.12.
- [GHSA-jcc5-8wj4-7c58](https://github.com/LibVNC/libvncserver/security/advisories/GHSA-jcc5-8wj4-7c58): Tight Gradient corruption, with no patched version named in the advisory metadata inspected.
- [GHSA-87q7-v983-qwcj](https://github.com/LibVNC/libvncserver/security/advisories/GHSA-87q7-v983-qwcj): UltraZip bounds issue, range through 0.9.15.

The [accepted bounded source review](../../07-reference/2026-10-15-vnc-patched-source-selection.md) resolves this source-coverage question at `98aaee0560baa0332339b2ef464ea96ed9b9b28c`: Tight rows `540332be…`, Gradient width `5b270544…`, UltraZip `009008e2…`. Before an ordinary server probe, reuse or add only the missing focused advisory regressions, including valid decode controls; normal encoding evidence requires nonzero per-encoding update counts and zero failures, not merely exit 0. The inspected upstream workflow/check conclusions do not establish advisory-specific runtime results; the selected Android build and adapter remain untested. Stop once these bounded checks pass or expose a concrete blocker; do not recreate a general RFB audit. TLS or SSH protects transport identity/confidentiality but does not repair a malicious-server decoder bug; restricting advertised encodings alone is not accepted fix evidence.

## First real Linux-first probe and stop conditions

1. Build the pinned reduced FreeRDP Android library/ABI in isolation; record tool identities, source/dependency hashes, selected options, compiler output and packaged `.so`/AAR hashes. Inspect CMake/Gradle configuration and compiler/static-analysis results. Stop on a concrete toolchain/dependency failure and research that failure only; do not downgrade to an older insecure release merely to get a build.
2. Add the smallest real qualification screen after leader review: native framebuffer view, explicit connect/cancel/disconnect, endpoint and private credential entry, deliberate certificate decision, bounded status, and no background reconnect. Compile and Android Lint the changed module; test Cloudy's adapter cancellation/trust/input ownership. No fabricated framebuffer/session or log-only action counts.
3. Identify the actual Ubuntu 26.04 desktop/compositor, server installation and backend version before selecting or enabling a fixture. This workstation's Wayland label does not imply GNOME; a KDE session needs its own supported server investigation. GNOME Remote Desktop is a candidate only for an applicable installed session; its [upstream README](https://github.com/GNOME/gnome-remote-desktop/blob/master/README.md) distinguishes active-session assistance, headless single-user and RDP-only system remote login. Assistance closes on screen lock according to that source. Select active-session assistance first if locally available; qualify lock/session behavior separately. Do not assume the moving README's VNC support is compiled into the installed Ubuntu package. Ubuntu's desktop-sharing help returned HTTP 503 in this research; no local readiness was inferred.
4. With the reviewed fixture/server and actual Googlebook, connect, reject an untrusted/changed identity, authenticate deliberately, display changing real desktop pixels, type real text and click/scroll, resize if negotiated, release held keys/buttons on focus loss, cancel an in-flight connect, disconnect and verify resources stop. Capture actual security/graphics/transport negotiation, exact host/server/device/APK identities and scoped evidence. If the reduced renderer cannot negotiate with the available server, record the actual requirement before enabling a codec. No Windows target is available and none is needed for this Linux-specific result.
5. Once the accepted VNC candidate passes its focused regression/build prerequisites and license entry is resolved, use an actual ordinary VNC server on a protected route. GNOME package capability may supply it; otherwise separately qualify an appropriate server/session. A virtual X display is a distinct session from the workstation's Wayland desktop. Require verified encrypted security or authenticated SSH transport owned by Desktop itself; do not depend on Console's credentials/process. Carry forward the same framebuffer/input/cancel boundaries and record actual RFB encoding/security.

A representative successful Cloudy connection with failure/cleanup checks closes this entry investigation. P0-S4 still requires its independent streaming, decoder/performance and physical-input cases; P3 native product gates remain blocked until their own accepted integration and licensing evidence exists.
