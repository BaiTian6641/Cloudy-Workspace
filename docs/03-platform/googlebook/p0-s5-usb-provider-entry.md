# P0-S5 — USB provider entry and bounded build decision

**Reviewed source date:** 2026-10-15, America/Chicago. **Owner:** Android/USB integration leader. **Status:** source investigation; proposed build entry, no provider adoption or CAP-USB promotion. This note preserves full general-purpose USB scope and the [enrollment/ownership contract](../../02-architecture/usb-plug-and-play.md). The selected primary consumer is the Ubuntu workstation. A physical peripheral/probe remains deliberately unspecified; no attach, reset, driver detach or programming operation was performed for this review.

**Implementation follow-up:** the separate [native USB source/build review](../../06-validation/2026-10-15-native-usb-review.md) now records a real0.1.0 diagnostic with pinned libusb1.0.30, compiler/Lint and20JVM tests. The source facts and proposed provider adoption below retain their original evidence boundary; actual device observations require a separate run. No exporter or consumer adapter is implemented by this probe.

## Decision

Carry forward **external VirtualHere Android provider plus Linux consumer** as the first practical route for locally attached Googlebook USB to the actual Linux workstation. Build a narrow consumer adapter with explicit unavailable/manual-provider states before attempting a new USB virtualization stack. This is a candidate decision, conditional on exact release/terms, actual consumer API and provider qualification. External setup is a partial milestone; it does not complete integrated enrolled plug-and-play.

A rootless Android **userspace device-access entry** is documented: `UsbManager.openDevice()` → `UsbDeviceConnection.getFileDescriptor()` → `libusb_wrap_sys_device()`. It is suitable for a bounded native access probe and a future reusable export backend. It supplies neither a USB-over-network exporter nor workstation import by itself. No reviewed established libusb-based Android USB/IP exporter has been selected. Do not silently turn that missing component into Cloudy-authored virtualization under the [reuse policy](../../05-delivery/library-reuse-policy.md).

`usbredirhost` is an established userspace exporter candidate, but its established receiving route is a virtual USB controller in QEMU/SPICE guests. That is a different topology from importing a peripheral into the selected workstation's own kernel and applications. Do not add a VM or a usbredir-to-USB/IP translator as an invisible prerequisite. Keep this as an alternate lab/VM provider lane only if that topology is explicitly selected later.

## Smallest implementation entry

Timebox the first software increment to **one engineer-day** after leader acceptance. It can proceed without an available peripheral. Stop when the adapter performs genuine bounded observations and returns explicit reasons for missing prerequisites; do not extend into a replacement protocol stack.

1. Implement a host-local VirtualHere consumer adapter using a configured absolute executable, argument arrays and bounded subprocess output/deadline. Allow only read-only `HELP`/state/information operations initially. Discover executable absence, non-running consumer, command failure, incompatible state/version and timeout as distinct real results. The executable is an independently installed dependency; no automatic download, daemon, server or elevated launch is part of this increment.
2. Parse only the pinned observed state format with bounded input and external-entity handling disabled. Separate endpoint connectivity, provider observations, claimed consumer owner and tool readiness. Persist enrollment intent separately from observations; restart begins unknown. Without a running provider/consumer, expose unavailable/unknown and next action. Test-only recorded/synthetic XML fixtures are parser/state evidence, never attached-device evidence.
3. Add mutation only after `HELP`/state/version evidence and the trust boundary are reviewed. `USE`/`STOP USING` must require an enrolled exact destination and fresh expected generation/owner. Gate protected/unknown/busy states. After timeout, query; never blindly repeat a toggle or release someone else's device. Do not include global stop/auto-use-clear commands in the initial allowlist.
4. Expose these operations remotely only through an authenticated narrowly scoped host adapter. Ordinary SSH can transport finite adapter requests where qualified; no permanently running shared daemon, borrowed Console credentials or mandatory custom host agent. An API adapter is not by itself the bulk USB transport. Provider network traffic needs an explicitly qualified private route or vendor-supported TLS and identity policy; no unauthenticated public listener is proposed.
5. Optionally compile a separate Android grant/FD probe with pinned libusb1.0.30 and the existing Android toolchain. It enumerates through `UsbManager`, requests access only for the selected device, wraps the real FD without discovery, reads locally available descriptor information, and closes resources in ownership order. Do not open ADB/debug transport or unrelated system peripherals. No hardware means only build and unavailable-state evidence, with granted-device execution pending. Do not bundle libusb solely to decorate a nonfunctioning Export button.

Meaningful checks: adapter AST/compiler/lint plus real subprocess missing executable/non-running/deadline behavior; focused parser bounds/malformed/version mismatch tests; generation/timeout/protection tests for authored orchestration; documentation validation. Android code, if introduced, must compile and pass Android Lint and native compiler checks; runtime JNI load is separate evidence. Reuse upstream USB/parser validation; do not rebuild a USB conformance suite. A new dependency requires a pinned source/hash, notices and review before acquisition/build.

## Immediate Android qualification APK specification

The leader may implement this probe first, independently of external provider installation. Create a separate qualification package so terminal/RDP artifacts and journals remain unaffected. Use the repository's current Android37 compile/target, minimum35 and NDK **29.0.14206865** baseline, as recorded in `qualification/probes/native-rdp/app/build.gradle.kts`; restrict the first native package to `arm64-v8a`. These are local build choices, not libusb minimum requirements or completed compilation.

Use libusb **v1.0.30**, pin the release archive SHA256 before use, and record `libusb_get_version()` at runtime. Prefer upstream's existing NDK shared-library target rather than inventing a Linux build configuration: [android/jni/libusb.mk](https://github.com/libusb/libusb/blob/v1.0.30/android/jni/libusb.mk) selects the Linux usbfs/POSIX/netlink sources, Android config include directory, hidden visibility, pthread and log linkage. Its `USE_PC_NAME=1` produces module `usb-1.0`; otherwise the legacy module is `libusb1.0`. Include only that library recipe through a small project-owned ndk-build wrapper; the top-level [Android.mk](https://github.com/libusb/libusb/blob/v1.0.30/android/jni/Android.mk) also includes upstream examples/tests, which are unnecessary APK content. Explicitly set `APP_ABI=arm64-v8a` and `APP_PLATFORM=android-35`; upstream [Application.mk](https://github.com/libusb/libusb/blob/v1.0.30/android/jni/Application.mk) defaults to all ABIs. Add a tiny JNI library linked against the resulting shared libusb and package both; verify actual ELF dependencies, exported JNI symbols, runtime load and16KiB alignment with the established audit approach. No libusb binary was built or hash asserted in this research.

JNI initialization should create an explicit context using one `libusb_init_option` with `.option = LIBUSB_OPTION_NO_DEVICE_DISCOVERY`, passed to `libusb_init_context(&ctx, &option, 1)`. Report the actual return code and loaded version; initialization does not discover or open devices. The Android layer calls `getDeviceList()` and reports zero devices honestly. It must never use libusb's global enumeration as an alternate route around Android grants. A user selects an eligible non-system peripheral before permission/open; absence, rejection, grant-pending and open-null are separate outcomes. Do not install a catch-all attach intent filter that competes for every peripheral.

A single serialized owner executor controls context/connection/native-handle state. Keep the actual `UsbDeviceConnection` alive while native code borrows its FD; never independently `close(fd)` on that borrowed descriptor. Wrap with `libusb_wrap_sys_device(ctx, (intptr_t)fd, &handle)`, and inspect the wrapped device descriptor only. Do not call `libusb_claim_interface`, reset, configuration/alternate-setting changes, control/bulk/interrupt/isochronous transfers or kernel-driver detach. Wrapping is nonblocking in upstream documentation, but its real kernel/permission behavior still needs runtime observation. Descriptor access must report exact errors; it cannot count as forwarding.

Cancellation marks that connection generation invalid immediately and queues cleanup on the same executor. A pending permission response is not cancelled by closing a nonexistent FD: ignore stale responses, recheck current device presence and `hasPermission()` before `openDevice()`, and close any connection opened after cancellation. `ACTION_USB_DEVICE_DETACHED` invalidates the selected generation; stop scheduling work and close native handle, then Java connection, then context once no native call can touch it. Never close a native resource concurrently. Physical removal can precede the broadcast; errors such as `LIBUSB_ERROR_NO_DEVICE` enter the same cleanup path. Replug is a new generation requiring fresh observation/grant/open. Activity recreation may retain a visible process-owned diagnostic state; process death restores only intent and an interrupted/unknown report, never a live pointer/FD or a presumed grant. The first probe has no background service or background-forwarding claim.

Tests cover stale grant after cancel/detach, generation changes, open failure, native wrap failure and exactly-once ownership-order cleanup through test-only adapters. Compile/lint/JVM/native checks plus a real no-peripheral load/enumeration run can close this software increment. Granted-device wrapping, deny/replug races on physical hardware, driver access, forwarding, reset and programming stay pending. This deliberately useful probe measures the platform boundary while the full VirtualHere/native-export requirement remains open.

## Acceptance boundary and deferred prerequisites

The immediate deliverable is a real provider/consumer readiness adapter, or its honest unavailable result. It is not USB forwarding. Full P0-S5 remains incomplete until a representative actual device/tool performs attach and program/verify with exact firmware/backend/build identities. P3-S6 retains 30-cycle enrolled hotplug, ownership, denial, restart, contention and approved re-enumeration evidence. Serial-only success cannot qualify arbitrary classes; retain distinct bulk/control/interrupt/isochronous/composite and reset-sensitive support rows.

Re-enumeration closes the old Android connection and permission generation. Approved runtime/bootloader aliases need actual hardware identity and same-owner reconciliation; no saved FD, VID/PID-only match or timer implies authorization. Never replay a programming operation. Protected uncertainty stays protected until authoritative reconciliation.

Open prerequisites are exact VirtualHere Android version/signature and supported control surface, vendor license/redistribution terms, Linux import availability/privileges, authenticated transport, selected representative peripherals and actual Googlebook lifecycle/grant/reset behavior. The source pages do not settle these. If external provider automation remains unavailable, retain manual setup as partial and the integrated requirement open. A lab-side provider is an explicit alternate topology and does not fulfill local Googlebook plug-and-play. Reopen native exporter selection only for a concrete provider-control/licensing/compatibility failure with an identified maintained alternative and a bounded comparison question.
