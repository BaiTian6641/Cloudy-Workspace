## Reproducible setup and resolved documentation mismatch

The Android 17 setup guide G36 uses `compileSdk = 37`, but its manual steps retain preview wording. The inspected stable SDK repository calls the base package `android-37.0`; there is no `platforms;android-37` entry in that manifest. Select the explicit minor-0 DSL and exact package rather than renaming an SDK directory or weakening the requested target. Installed package metadata is retained locally; the build must prove the resolver accepts it.

Set `ANDROID_HOME` to the chosen SDK, `ANDROID_USER_HOME` to a writable tools preference/cache directory, and `GRADLE_USER_HOME` to a writable Gradle cache. These variables are command-local; do not change the user's shell configuration. The initial SDK-manager failure described a missing package, but verbose output showed its default user cache was read-only. Setting the documented `ANDROID_USER_HOME` resolved the failure without changing network trust or host permissions (G38).

Existing accepted SDK license records were reused in the isolated SDK root. New license prompts require reading the presented terms; do not pipe an unconditional acceptance into installation. CI uses the hosted runner's existing Android SDK license records and verifies the selected command-line tools archive before invoking its SDK manager.

Command-line tools 22.0 warn that `sdkmanager` is deprecated in favor of Android CLI. Invoking the bundled `android --help` launcher unexpectedly bootstrapped its CLI into the isolated Android user directory. That first help invocation was not an intentional CLI version selection; it printed a metrics notice. A subsequent `android --no-metrics --version` reported `1.0.16500706`. Further CLI use must explicitly disable metrics and review the resolved tool before relying on it. The reproducible build and CI use the verified SDK-manager package and Gradle wrapper, not that automatic CLI update route. No shell profile, global skills, or device service was changed by this bootstrap.

AGP's analytics helper also reads the older SDK preference setting. When both variables are needed, `ANDROID_SDK_HOME` must be the parent of `ANDROID_USER_HOME` ending in `.android`; inconsistent locations are rejected. The tested local pair is project cache `android-user` and its `.android` child. Keep both local and do not repurpose the system home directory. Kotlin's default daemon attempted a read-only user-data directory; the probe uses the official [in-process compiler strategy](https://kotlinlang.org/docs/compiler-execution-strategy.html), preserving the same compiler and warning policy.

Dependency lockfiles and Gradle SHA-256 verification metadata record the selected dependency graph. The metadata is a reviewed first-resolution integrity baseline from Google Maven/Maven Central/plugin repositories, not a third-party signature attestation. Normal builds verify it; do not run `--write-verification-metadata` in CI or blindly accept changed hashes.

Run the commands in the probe README and [Android probe workflow](../../../.github/workflows/android-probe.yml). Compiler and Android Lint checks are required alongside the repository AST/lint/documentation checks. A successful build does not qualify a Googlebook API or remote backend.

The first Android Lint run reported only the Gradle update advisory: 9.8.1 is available while the selected AGP 9.4 compatibility baseline is 9.6.0. The probe keeps that intentional pin, with a file-specific `AndroidGradlePluginVersion` exclusion for the wrapper properties. All other lint findings remain errors. Revisit the pin deliberately when updating the toolchain rather than silently downloading the newest release.

A clean-cache build exposed five transitive metadata entries omitted by the initial warm-cache generation: Guava parent 33.4.0-jre, JUnit BOM 5.10.2/5.11.0-M2 module metadata, coroutines BOM 1.8.0 and Groovy BOM 4.0.29. Each added SHA-256 was checked against a separate canonical Maven Central download and the clean Gradle cache. The clean checkout then passed all 49 assemble/lint/test tasks with verification enforced; application dependencies and source were unchanged.
