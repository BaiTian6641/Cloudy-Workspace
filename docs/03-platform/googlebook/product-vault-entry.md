**Checked:** 2026-10-16. **Status:** reviewed implementation entry; no product vault implemented or qualified. **Owner:** integration leader and Android security developer, P1-S3. ## Real bounded increment

Implement shared source in a new `shared/android/identity` module, instantiated independently in Console and Desktop. Each owning app has separate files, aliases and authorization; neither uses the diagnostic streaming identity or the other app's credentials. Android Keystore provides app-local non-exportable keys, with hardware protection conditional on the generated key. Inspect actual `KeyInfo.getSecurityLevel()` (API31) and authentication enforcement; do not infer AES backing from RSA evidence. [Keystore guide](https://developer.android.com/privacy-and-security/keystore).

Provide actual user-visible **Save on this device**, authorized scoped use and deliberate deletion. A bounded instrumentation consumer may verify decrypted bytes without displaying/logging them; it establishes storage/use, not remote authentication. Do not add a fabricated Connect action. Keep default per-session entry available when saved credentials cannot meet policy.

## Binding, crypto and storage

Define an immutable versioned binding from the outset: owning package, protocol, canonical endpoint/port, target-or-gateway role and an opaque account-binding ID. Keep logical TLS identity distinct from transport/tunnel address. No reserved placeholder binding or display-name substitution. Account metadata and secrets belong inside ciphertext; plaintext envelope fields contain only bounded format/algorithm identifiers, random record ID, key version, IV and ciphertext/tag. The local profile may retain the random opaque account-binding ID with its credential handle; the actual username/domain and secret remain encrypted. This lets a fresh process construct expected AAD without storing or guessing the account body in plaintext. An endpoint/account change creates a newly authorized binding; the display label is never the identifier. The caller supplies the expected binding for authenticated verification.

Use standard `KeyGenerator` with `AndroidKeyStore`, AES256, encrypt/decrypt purposes, GCM, no padding and randomized encryption. Initialize encryption without an IV, retrieve the provider-generated IV and use a 128-bit tag. Authenticate the immutable binding plus schema and record ID with `Cipher.updateAAD` before `doFinal`; never release partial decrypted output. Reject changed binding, unknown format, malformed lengths and tampering. G104 covers [Cipher](https://developer.android.com/reference/javax/crypto/Cipher); G133 covers [KeyGenParameterSpec.Builder](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder). The AndroidKeyStore AES key-generation path requires API23; Cipher.updateAAD requires API19, both below app min35. No custom cipher or plaintext fallback.

Derive each dedicated alias from an internal fixed namespace and a strictly validated canonical random record ID/key version. Never accept an arbitrary alias from a file for lookup or deletion. Missing/invalidated keys make existing ciphertext unavailable; do not regenerate a key and imply recovery.

Store bounded envelopes in credential-encrypted `Context.getNoBackupFilesDir()` (API21), never device-protected/external storage. Preserve explicit cloud/device-transfer exclusions and `allowBackup=false`; manufacturer-dependent transfer behavior still needs its own qualification. G137: [storage API](https://developer.android.com/reference/android/content/Context#getNoBackupFilesDir()); [backup rules](https://developer.android.com/identity/data/autobackup).

Serialize disk/Keystore operations off-main through one owning worker. G50 [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile) (API17) supplies `startWrite`, `finishWrite`, `failWrite`; it does not synchronize writers. Validate readback before commitment. Interrupted creation retains explicit incomplete metadata without secrets; do not silently adopt/overwrite orphaned keys. Deletion first makes use unavailable, then retains a bounded tombstone until the owned key and record are absent and cleanup completion is persisted and verified by readback. Failure stays `DELETE_PENDING`; explicit local cleanup retry performs no network work. No physical flash-erasure promise.

## Authorization and lifecycle

Preserve the reviewed time-based policy: `setUserAuthenticationRequired(true)` (API23), `setUserAuthenticationParameters(30, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL)` (API30), and `setUnlockedDeviceRequired(true)` (API28). App min35 avoids the documented older unlocked-device bugs. Combined credential authorization does not promise invalidation on new biometric enrollment. [Builder reference](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder).

Use the existing AndroidX `BiometricPrompt` contract, initially the accepted device-credential route, without a per-use CryptoObject. Actual dependency selection and Activity integration require parent review; this entry neither selects an unverified version nor substitutes the platform prompt. [AndroidX prompt reference](https://developer.android.com/reference/androidx/biometric/BiometricPrompt).

Mint a one-use in-memory token only from the actual current prompt callback, binding window/attempt generation, operation, credential, immutable binding and monotonic callback deadline. Check cancellation, visibility and deadline before crypto and before scoped consumption. No authorization in saved state; process restoration never decrypts/replays. Backgrounding revokes admission and cancels pending prompts. Return `AUTH_REQUIRED` on authentication failure; never automatically re-prompt. Wipe mutable supplied/plaintext buffers on every path, without claiming complete JVM/native zeroization. Logs contain bounded codes, not secrets, account bodies, endpoints or credential material.
