## Historical defect and evidence boundary

The prior diagnostic **0.1.4/code5**, build reference `dc833678-46b0-47e3-bb4e-1a9cc804cbf5`, implements standard negotiated relative input. Its cursor presentation was incomplete:

- `RdpSession.pointer()` updated `frame.move(x, y)` for absolute input. `sendRelativeOnOwner()` submitted relative input and incremented counters without moving the rendered cursor.
- `RdpFrameBuffer.draw()` drew a custom cursor at its last stored position. `defaultPointer()` cleared the bitmap; there was no software default-arrow path.
- The 0.1.4 native Android bridge's `android_Pointer_SetPosition()` returned TRUE without forwarding coordinates. Java handled cursor shape/default/hidden notifications but had no position callback. Shape handling already existed; not every cursor update was missing.

Inspect the [session](../../../qualification/probes/native-rdp/app/src/main/java/dev/cloudy/qualification/rdp/RdpSession.kt), [framebuffer](../../../qualification/probes/native-rdp/app/src/main/java/dev/cloudy/qualification/rdp/RdpFrameBuffer.kt) and [Java ABI](../../../qualification/probes/native-rdp/app/src/main/java/com/freerdp/freerdpcore/services/LibFreeRDP.java) against the accepted source identity before editing. The exact upstream [Android pointer callbacks](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/Studio/freeRDPCore/src/main/cpp/android_freerdp.c) and [pointer cache dispatch](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/libfreerdp/cache/pointer.c) establish the position-callback entry point. Retain the reviewed patch chain; upstream source alone does not identify Cloudy's complete native build.

Android makes the system mouse pointer invisible while capture is active. A default cursor can therefore disappear, and a custom cursor can remain at the last absolute location even while relative events reach the host. This is a concrete client defect, not proof that it caused every reported movement failure. [Official Android capture contract](https://developer.android.com/develop/ui/views/touch-and-input/gestures/movement#pointer-capture), API26+.

The retained 0.1.4 [physical-cursor exercise](../../../qualification/results/P0-S4/2026-10-15-rdp-physical-cursor.md) reports **captured movement fails and local release works**. The retained observation has **873 accepted relative JNI submissions** and **504 target mouse moves after capture confirmation**. The release edge is unknown, so those moves cannot be attributed specifically to the captured interval. Keep the counts, user observation and attribution limit together; neither a relative-delivery pass nor a total transport-failure conclusion follows. The earlier KRdp missing-relative-callback failure remains separate from this GRD/client-presentation question.

GRD 50.2's [cursor renderer](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/src/grd-rdp-cursor-renderer.c) emits cursor shape/default/hidden updates; no `PointerPosition` emission was found in that inspected file. An authoritative position bridge alone may therefore be insufficient for this exact server. Its [relative input callback](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/src/grd-session-rdp.c) and [libei dispatch](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/src/grd-session.c) are distinct from cursor presentation; the bounded host-trail observation below supplies runtime evidence without assuming every input or cursor case is qualified.

## Implemented repair and protocol invariants

Diagnostic **0.1.5 / code6**, build reference `a5a5db42-1444-4642-bfff-aa63751a8e4f`, implements the following authored boundary:

1. **Authoritative position:** the sixth native patch forwards maintained `SetPosition(context, x, y)` through Java `OnPointerSetPosition(long, int, int)` to instance-checked `Sink.pointerPosition`. The session validates current framebuffer bounds, rejects retired instances and retains numeric-only first-failure diagnostics. Real server positions reconcile the synchronized cursor state; they are never echoed as mouse input.
2. **Visibility and shape:** default-visible, custom-visible and server-hidden states are distinct. Confirmed capture can draw an original software default arrow while Android hides its system pointer. Custom shapes retain hotspot validation and clipping. A server-hidden state remains hidden, including applications intentionally hiding the cursor for relative operation.
3. **Presentation-only prediction:** only a successful relative JNI admission advances the clamped predicted position. The UI labels prediction, server feedback, admitted absolute input and an initial center estimate separately. Connection, geometry and capture-ownership changes reset prediction to known feedback or that explicit estimate. An authoritative revision crossing JNI admission suppresses the local delta rather than applying it again over the server correction. No agreement with server acceleration, constraints, warps or application consumption is assumed.
4. **Redraw ownership:** absolute movement, admitted relative prediction, shape changes and real position callbacks request the existing coalesced UI notification. Framebuffer drawing/cursor replacement retain the shared synchronization and bitmap-lifetime rules; no per-delta unbounded main-thread queue or forced bitmap recycling is introduced.
5. **Wire nonregression:** the accepted signed-delta JNI/queue/core path, capability checks, wheel routing, button/modifier release ordering and local release action remain intact. Presentation prediction emits no absolute movement, recentering or AINPUT fallback. A moving client cursor remains distinct from observed host response.
6. **Capture evidence:** an attempt-scoped journal stores at most 32 capture edges separately from the 80 native events. Request, framework confirmation, release request, actual released/lost callback, timeout and rejected grant are distinct. Synchronous UI-edge time/input counts and later owner-observation time/counts are stored separately. Stale/retired attempts are rejected; reap can persist captured evidence even if it beats the queued evidence task.

The controlled host target now paints its actual own-window motion marker/trail and event count as **host-motion-1**. Those pixels derive from received host events, not Android deltas or client prediction. The trail therefore provides a separate visible observation when comparing local cursor feedback with remote application response.
