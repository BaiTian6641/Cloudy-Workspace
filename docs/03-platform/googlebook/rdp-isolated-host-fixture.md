# Isolated GNOME RDP host fixture

**Checked:** 2026-10-15. **Stage:** P0-S4. **Outcome:** a real extracted GNOME Remote Desktop/Mutter headless fixture now starts, renders through a software compositor and presents the controlled target on the RDP-created output. This is method and readiness qualification. Physical standard-relative movement, repeated release/focus cases and actual 3D interaction remain pending; CAP-RDP remains pending.

The parent owns fixture execution, the final run report and its evidence manifest. Raw logs, generated authentication material and machine-specific paths remain private. The earlier static readiness inventory is historical: package availability, an ELF dependency walk and schema checks alone did not demonstrate startup. The six actual startup attempts below supersede that inventory for the method described here.

## Purpose and selected components

The [relative/portal result](../../../qualification/results/P0-S4/2026-10-15-rdp-relative-portal.md) retains the KRdp 6.4.5 result: negotiated relative capability and accepted JNI submissions did not produce observed remote cursor movement. Its source investigation identified the absent standard relative callback in that server. This separate fixture preserves the real standard RDP client path and supplies a maintained server with a concrete relative-input consumer.

The fixture uses extracted Ubuntu packages **GNOME Remote Desktop 50.2-0ubuntu0.1**, **Mutter/libmutter 50.1-0ubuntu2.4** and **FreeRDP server 3.32.1+dfsg-0ubuntu0.26.04.1**. The selected host already supplies **PipeWire 1.6.2**, **WirePlumber 0.5.13**, **libei/libeis 1.5.0**, **D-Bus 1.16.2** and **Bubblewrap 0.11.1**. Nine exact package archives were hash-checked against package metadata and extracted privately, including the missing server/TPM-return-code/GNOME-desktop libraries and Mutter/common schema data. No package installation or GNOME Shell/GDM activation is required by the accepted method.

GNOME's [50.2 tests](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/tests/run-rdp-tests.py) launch bare Mutter headless and the real headless server. Their [environment wrapper](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/tests/prepare-test-environment.sh) and [PipeWire runner](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/tests/pipewire-test-runner.sh) establish the isolation pattern. Cloudy's fixture adapts that pattern to extracted packages, preserves the ambient home variable and uses explicit private XDG directories.

GRD 50.2 enables the standard relative capability and assigns `RelMouseEvent`; its [RDP callback](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/src/grd-session-rdp.c), [event queue](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/src/grd-rdp-event-queue.c) and [session dispatch](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/src/grd-session.c) lead to `ei_device_pointer_motion`. This inspected chain makes it a suitable next candidate. It does not establish that a particular physical device event reached that chain or a target application.

## Namespace, rendering and authentication method

A finite parent-owned supervisor creates separate user, network and mount namespaces, followed by a Bubblewrap PID/mount view. It enables only the new network namespace's loopback interface **before** entering Bubblewrap. That ordering avoids granting network-administration capability to the fixture daemons; the first actual attempt showed that the later `ip` operation failed. See [R199: Bubblewrap capability handling](https://raw.githubusercontent.com/containers/bubblewrap/v0.11.1/bubblewrap.c).

GRD's reviewed bind helper uses `g_socket_listener_add_inet_port`, so its wildcard socket is confined to the isolated network namespace. A private pathname UNIX relay carries unchanged RDP bytes between that namespace and an owned host-loopback TCP listener. Any device reverse route is a separate parent-owned operation. There is no host-interface, firewall or route change. The relay and software rendering make this a functional input fixture, not a performance fixture.

The fixture starts a private session D-Bus, PipeWire and WirePlumber directly. Configuration, data, state, cache and runtime directories are private; the ambient `HOME` value is preserved. The private mount view keeps the root filesystem read-only except for owned run data and temporary mounts. Physical GPU/audio/TPM devices and the host system bus are unavailable. The actual successful Mutter log records a **surfaceless renderer without a GPU**; software rendering is now observed startup behavior, rather than only an environment-variable intention. Optional system-service proxy warnings do not imply those host services were enabled.

AppArmor mediation remains enabled. Its decision-query ABI opens `/sys/kernel/security/apparmor/.access` with `O_RDWR`, writes a query and reads the decision. Making that endpoint read-only caused actual private-bus failures. The fixture therefore binds **only that query file** writable inside its private mount view; policy-control files and the rest of the security filesystem remain read-only. This permits the normal mediation query without disabling AppArmor or D-Bus policy. [R197: exact libapparmor 5.0.2 query implementation](https://gitlab.com/apparmor/apparmor/-/raw/v5.0.2/libraries/libapparmor/src/kernel.c), [R198: D-Bus query error path](https://raw.githubusercontent.com/d-bus/dbus/master/bus/apparmor.c). R198 explains the observed error string; it is not exact provenance for the installed D-Bus binary.

Fresh private fixture credentials and a short-lived TLS key/certificate are generated per run. Configuration uses normal `grdctl --headless` operations. The random fixture username is supplied through the public one-argument `set-credentials` form; **only the password is supplied on stdin**, with no password argument or credential environment hook. Feeding username and password as two lines to separate buffered prompt readers produced an actual `grdctl` crash; the one-prompt form avoids that observed input-buffer boundary. The enable flag uses the upstream test's direct GSettings route, because `grdctl enable` invokes the service-enable helper. No system or user service is enabled. The Android diagnostic still applies endpoint-bound certificate pinning and normal NLA; fixture provisioning is not the product credential vault.

The extracted Mutter process receives an **absolute `--mutter-plugin` path** to its shipped `libdefault.so`. Its compiled default directory belongs to a system installation and did not resolve the extracted plugin. [R195: standalone option](https://raw.githubusercontent.com/GNOME/mutter/50.1/src/core/mutter.c), [R196: absolute-path loader behavior](https://raw.githubusercontent.com/GNOME/mutter/50.1/src/compositor/meta-plugin-manager.c).

## Display creation and target ordering

GRD's headless settings select **EXTEND**. A manually created bootstrap monitor is a separate output; a window opened there is not automatically mirrored onto the output created for the RDP client. The accepted launch order therefore starts Mutter with **no bootstrap virtual monitor**, starts GRD, connects the real RDP client and lets GRD create its output, then starts the controlled Wayland target on that compositor. The target must use the fixture's Wayland socket and private runtime. [R194: headless EXTEND settings](https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/50.2/src/grd-settings-headless.c).

The finite supervisor exposes an explicit target-start signal after connection. Target lifetime is shorter than the fixture's maximum active duration. A normal target exit is controlled completion; unexpected component exits fail the fixture. Active duration begins at readiness and is capped at600 seconds, with separate startup/command deadlines. Teardown terminates and reaps owned processes, handles relay descendants even when their leader already exited, and records actual key/configuration/credential-directory absence. Cleanup receipts must be inspected for each run; readiness does not establish later teardown.

## Actual startup attempts

These are **six fixture attempts**, separate from the numbered Android RDP journal attempts in the existing result. Their detailed logs and run directories are private.

| Fixture attempt | Actual observation | Method correction or limit |
| --- | --- | --- |
| 1 | Network setup failed: `ip` exited 2 before PipeWire, Mutter or GRD started. | Move loopback setup into the newly owned network namespace before Bubblewrap capability restriction. |
| 2 | Argument parsing exited 2 before daemon execution. | Preserve the nested Bubblewrap continuation verbatim rather than letting a nested `--` terminate the outer parser. |
| 3 | PipeWire/WirePlumber started; `grdctl` exited with signal 11 during credential setup. Private-bus operations also reported an AppArmor query read-only error. | Use nonsecret username argument/password-only stdin and expose the single AppArmor decision-query endpoint with its required access mode. These are separate observed boundaries; the bus error alone does not prove the crash cause. |
| 4 | Mutter exited 1 before readiness because its default plugin path did not resolve. | Select the extracted plugin through the absolute public option. |
| 5 | Namespace and host-loopback readiness succeeded, but the client saw the background while the target occupied the bootstrap output. | Headless EXTEND requires creating the client output first and starting the target afterward. Parent stopped this run deliberately. |
| 6 | Namespace and host-loopback readiness succeeded with the no-bootstrap method; the real controlled target was presented on the connected output. Mutter recorded a surfaceless renderer and creation of the RDP virtual monitor. | Suitable fixture readiness for the next physical input experiment. No physical relative-movement, release or 3D pass is claimed here. |

The first five attempts have cleanup receipts showing the owned outer groups absent and generated key/client configuration/credential directory absent. Attempt 5's target ended by operator signal rather than normal target completion. Attempt 6 subsequently completed at the target deadline; the [final run report and manifest](../../../qualification/results/P0-S4/2026-10-15-rdp-isolated-host.md) record controlled input, explicit native cleanup, owned process-group absence and removal of generated credentials and routes. Physical relative input remains unqualified: the user's later response supplied no movement or release observation. Target event counts alone cannot attribute input to the remote transport when other controlled/manual stimuli are possible.
