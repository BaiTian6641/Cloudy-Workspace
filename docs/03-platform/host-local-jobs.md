# Bounded local jobs

**2026-10-16; Linux local-job construction has a historical finite runtime result; Windows amd64 construction is source/compiler accepted with native execution pending.** This is an internal local library under `host/core/internal/jobs`, developed alongside the Android clients. The existing host0.1.2 executable, identity format and diagnostic remain unchanged. There is no jobs CLI, remote-execution endpoint, pairing or installed service in this increment. P4-S1 prerequisites and integration exits remain required; ordinary SSH is independent of this optional host software.

## Caller authority and admitted operation

The Linux caller supplies a trusted retained delegation-directory handle, lifetime context and immutable `Spec`. Linux `Start` validates the specification and creates one fresh child in the delegated cgroup-v2 domain. Windows amd64 `StartOwned(lifetime, spec)` instead creates and owns a fresh unnamed Job Object; it does not accept a fictitious delegation handle. It returns an explicit `Job` owner before asynchronous process launch. If preparation has already acquired resources and fails, the returned owner remains responsible for settlement even when accompanied by an error. Callers must retain a nonnil owner on every outcome.

The executable is an exact absolute existing regular file, with an explicit absolute existing working directory. There is no PATH lookup or implicit shell. Validation is not protection against replacement by a hostile same-user process; trusted invocation paths and membership ownership are preconditions. These input bounds are fixed for this initial library:

| Input | Limit and behavior |
| --- | --- |
| Arguments excluding argv0 | At most64;4096bytes each;32768bytes total; no NUL |
| Environment | Explicit nonnil list, at most64 entries/32768bytes; unique ASCII variable names; no NUL or ambient inheritance |
| Stdin | At most65536bytes, then closed |
| Stdout and stderr | Retain at most65536bytes each while continuing to drain; copied snapshots, saturating total counters and explicit truncation/saturation flags |
| Runtime | 1ms through30000ms, independently from observation |
| Settlement observation | At most5000ms per observation; kernel stalls remain owned uncertainty |

Admitted slices are copied before asynchronous use. There are no arbitrary caller I/O callbacks, PTY, disk output export, raw output logging or network side effects provided by the library. Returned bytes may contain secrets or terminal control sequences; only the explicit caller receives them. The trusted command itself remains capable of its normal OS-authorized effects.

## Linux exclusive child ownership

Duplicate the caller's retained directory descriptor with close-on-exec; validate actual cgroup-v2 filesystem and domain type. Create a cryptographically named exclusive child with handle-relative operations, retain its opened identity, and require its initial empty domain and required control access. The caller's original handle remains usable. The delegation root may contain the supervisor; it is never a kill target.

Use the pinned Go Linux `UseCgroupFD`/`CgroupFD` placement path to start in this child. Missing placement capability or permission refuses honestly, without an outside-cgroup fallback or start-then-migrate. Do not enable controllers, move existing processes, signal a guessed process group, or construct authority from `/proc/self/fd` paths. The selected upstream implementation uses `clone3` with `CLONE_INTO_CGROUP`; actual local placement requires native evidence. [Go1.27.2 Linux process implementation](https://github.com/golang/go/blob/go1.27.2/src/syscall/exec_linux.go)

The owned child's `cgroup.kill` and `cgroup.events` supply subtree termination and empty-membership observations. They do not establish direct-child reap or resource closure by themselves. Cloudy requires those separate facts before reporting retirement, then removes only its exact empty child and closes its duplicated parent handle. Failed queries, close, removal or uncertain start retain ownership. This is membership containment, not a security sandbox against same-user mutation or work delegated to an outside service. [Official kernel cgroup-v2 contract](https://docs.kernel.org/admin-guide/cgroup-v2.html)

## Windows creation-time ownership

The Windows amd64 implementation uses exact `golang.org/x/sys/windows v0.49.0` public wrappers and a fresh unnamed, noninherited Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. `CreateProcessW` receives `STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_JOB_LIST`, assigning the child to that object at creation before user code, and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` containing only its three real inheritable stdio handles. Attribute backing values and handles remain live until deletion. Unsupported assignment, permission or restrictive nested-job failures refuse without retrying outside the job; there is no start-then-assign fallback. The API is documented for Windows10/Server2016 and later; compilation is not an availability test. [Microsoft attribute contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)

Shared byte admission is followed by valid UTF8/NUL checks, `.exe` target restriction, CRT/CommandLineToArgv-compatible argument escaping and a final32767UTF16-unit command-line limit including its terminator. The environment remains exact: no ambient `SYSTEMROOT` injection, case-insensitive duplicate-name rejection, ordering by the validated ASCII variable names and a nonnull double-NUL block for an empty environment. Its final block is also capped at32767UTF16 units. Explicit caller choice of a command interpreter remains caller authority; the library does not add an implicit shell. This argument convention does not promise compatibility with every executable's custom parser.

After successful creation, exact process/thread handles and the process ID are retained before fallible release. A later setup error returns the actual process plus error internally; shared coordination still records actual creation, waits once and retires its owned container. A nil process/nil error is rejected. The first safe failure is preserved over later wait failure. `Job` remains the explicit caller owner on uncertain outcomes; it has `Cancel`, `Wait` and `Settle`, not a caller `Close` operation.

Windows `Reaped` means its retained process handle was observed signaled and the actual DWORD exit code read; exit259 is valid after that observation. It does not mean POSIX zombie collection. Direct-process exit is observed before a250ms pipe-drain window. An unresolved pump yields `IOCompletion=not-assessed` and permits owned descendant termination; it does not delay the exit trigger until the full runtime limit or claim complete output. The specific Job Object's `JOBOBJECT_BASIC_ACCOUNTING_INFORMATION.ActiveProcesses==0`, actual direct wait, pump joins and successful owned-handle/pipe closure are separate retirement requirements. [Job accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [QueryInformationJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject)

Pipe closes run as retained asynchronous operations; a later `Settle` observes those same operations. Unfinished close/join and failed raw-handle close remain uncertainty, with no blind retry of a potentially reused handle. Kernel stalls can exceed observation budgets. The upstream attribute-list `Delete` wrapper returns no error and hides its `LocalFree` result; that release-observability limit is retained explicitly. Concurrent uncoordinated broad-inheritance process creation in the same process must be excluded by the caller; the allowlist constrains this creation, not arbitrary other callers.

The selected x/sys version lacks the named JOB_LIST constant and basic accounting structure. Their small public ABI definitions are pinned to Microsoft win32metadata commit `0f012441d654d3bb7de898fdc664b5fcad52bdcc`; compile-time amd64 guards require48bytes and `ActiveProcesses` offset40. The [result manifest](../../qualification/results/P4-S1/2026-10-16-host-windows-jobs.json) records exact header hashes. [Pinned WinBase.h](https://github.com/microsoft/win32metadata/blob/0f012441d654d3bb7de898fdc664b5fcad52bdcc/generation/WinSDK/RecompiledIdlHeaders/um/WinBase.h), [pinned winnt.h](https://github.com/microsoft/win32metadata/blob/0f012441d654d3bb7de898fdc664b5fcad52bdcc/generation/WinSDK/RecompiledIdlHeaders/um/winnt.h)

## Lifetime, results and settlement

The first coordinator-committed stop reason wins: natural exit, cancellation, timeout or failed start. This is explicit ordering policy, not a claim about simultaneous wall-clock events. Actual start resolution, reap, exit status/signal and retirement are separate fields. A nonzero exit can be a successfully reaped command.

`Cancel` requests retirement once. `Wait(observerContext)` observes and never cancels or retries the job merely because its observer expires. After a stop, `Settle(observerContext)` can continue bounded observation/owned cleanup without launching again or repeating the kill request. One actual process waiter owns reap; I/O completion and resource joins remain separate observations. A failed kill is retained uncertainty, not a new automatic kill attempt. An uncertain report requires the caller to retain the `Job` and arrange explicit recovery; dropping the Go value is not cleanup.

On Linux, the library supplies nonblocking bounded collectors and a byte reader to established `os/exec` copying. `WaitDelay` assists pipe retirement after direct-child exit; separate job coordination handles cancellation and descendant termination. Pinned Go prioritizes a process `ExitError` over a copy error, so nonzero exit alone cannot establish complete output or observed I/O failure. Keep output-completeness assessment separate from actual exit and resource retirement. [Go1.27.2 os/exec](https://pkg.go.dev/os/exec@go1.27.2)

Errors expose fixed code/stage text and retain raw causes privately without `Unwrap`. No path, argument, environment, input or output is interpolated into general errors. Runtime and settlement budgets cannot promise prompt kernel termination. Supervisor crash/restart recovery is still unimplemented; the finite outer test service provides test safety only.
