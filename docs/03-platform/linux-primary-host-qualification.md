## Proposed backend routes and prerequisites

**SSH/SFTP first.** Establish an OpenSSH server with a reviewed bind/network policy, host keys, selected authentication and a functioning SFTP subsystem. Validate configuration before activation and test from the intended Googlebook route. A local SSH client is insufficient. The [Ubuntu OpenSSH guide](https://ubuntu.com/server/docs/how-to/security/openssh-server/) describes server setup and configuration testing. For X11 later, verify `X11Forwarding`, `XAuthLocation`, cookie isolation and remote X11 application dependencies using the [OpenSSH server manual](https://man.openbsd.org/sshd_config). Xwayland's presence is not a test of Cloudy's separate X11 windows. A durable terminal-session mechanism must be chosen and tested independently.

**RDP for the existing KDE session.** Evaluate a pinned KRdp build before considering a different desktop stack. Its [upstream README](https://github.com/KDE/krdp/blob/893757086b6c2dff09c04c01bcb745fab1ff8d3a/README.md) describes TLS certificates, NLA and H.264 Graphics Pipeline support, with VA-API or software encoding. Verify those negotiated requirements with the selected native FreeRDP client. The same README includes outdated Plasma 5.27 limitations and newer settings, so it cannot certify behavior on 6.5.5. Qualify logged-in sharing, screen selection, scale/input coordinates, lock/disconnect and reconnect explicitly; do not enable autologin to manufacture unattended support. Configure listener scope and credentials deliberately rather than copying the all-interface example or putting passwords in shell arguments.

**Separate-session RDP fallback.** [xrdp's upstream documentation](https://github.com/neutrinolabs/xrdp) identifies xorgxrdp/Xorg as its desktop route, with Xvnc as an alternative. This is a candidate for a separate remote session, not evidence that xrdp shares the user's existing KDE Wayland desktop. Record the session identity and desktop availability so the fallback cannot silently change the intended workflow.

**VNC on Wayland.** [TigerVNC 1.16.0's w0vncserver manual](https://github.com/TigerVNC/tigervnc/blob/v1.16.0/unix/w0vncserver/w0vncserver.man) documents sharing an existing display through a wlroots compositor or the RemoteDesktop portal. KDE qualification should investigate the portal route; do not assume wlroots-specific protocols exist. Pin the server/security configuration, require an authenticated protected transport, and verify resize, clipboard policy and input against the chosen RFB client. Xvnc would create an X desktop and is a separate-session fallback. A successful VNC connection alone does not certify the full Desktop acceptance cases.

**Wayland permission and lifetime boundary.** The official [RemoteDesktop portal contract](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) separates session creation, device selection, user consent and ScreenCast/PipeWire capture. Query the actual interface/version and granted device types. If a backend uses `ConnectToEIS`, it must obey that API's session/input rules; do not assume all installed backends use this path. Test refusal, revoked grants, session closure and monitor changes. Portal installation alone is insufficient.

**Sunshine/Moonlight performance lane.** Pin an upstream Sunshine package and Android Moonlight version before testing. The reviewed [Sunshine capture configuration](https://github.com/LizardByte/Sunshine/blob/63d35f702ee9e362e43263742981836ec0710384/docs/configuration.md) distinguishes KWin, wlroots, KMS and X11 methods; KMS requires additional capability, while `wlr` is compositor-specific. Investigate the selected build's KDE/portal path first. The [setup documentation](https://github.com/LizardByte/Sunshine/blob/63d35f702ee9e362e43263742981836ec0710384/docs/getting_started.md) distinguishes package capture support, including no KMS in its documented AppImage/Flatpak routes. Verify real render-device access, encoder profile selection and input-device permissions separately. AMD/amdgpu identity does not prove VA-API encoding. Start with a measured SDR profile, safe pairing, actual keyboard/relative-pointer tests and focus-loss release; HDR, headless and latency parity remain unqualified. Do not treat external Moonlight success as native Cloudy integration.

**USB consumption on the Linux host.** The [VirtualHere client documentation](https://www.virtualhere.com/usb_client_software) identifies Linux as a consumer using the kernel USB/IP client driver. Qualify the selected client/license, kernel import support, target device driver/tool permissions, and its [control API](https://www.virtualhere.com/client_api). The Android-side [VirtualHere provider](https://www.virtualhere.com/android) remains a separately qualified dependency. An installed `usbip` executable does not prove either endpoint. The board/probe, reset/bootloader identities and actual programming tool are unknown: no attach, ownership transfer, flash or reset test is authorized by an inferred target.
