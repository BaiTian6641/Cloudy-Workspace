## Inspect and hold boundary

Candidate 03, helper 0.1.1/code2, introduced explicit `inspect` and `hold` modes. Missing/unknown mode rejects before obtaining UiAutomation. Inspect uses public framework APIs without constructing or injecting MotionEvents, collecting a UI tree or credentials, starting VNC, or opening a network connection. It returns an actual active/focused default-display VNC root snapshot, root bounds and both Android clocks. This supplies the previously missing real inspection-clock collection route.

Hold still requires coordinates inside parent-inspected framebuffer content, exact root bounds, active/focused default-display VNC package and fresh actual inspection values. Both `SystemClock.uptimeMillis()` and `elapsedRealtime()` ages must be between 0 and 30,000 ms; the elapsed clock prevents suspend preserving an old uptime admission. MotionEvent timestamps and the requested hold remain on the proper uptime basis. Root containment alone does not prove framebuffer containment, and clocks do not authenticate boot/session identity: the leader must inspect the actual app/build/session and preserve same-boot continuity. See the [fixture instructions](../../qualification/fixtures/android-input/README.md).

Candidate 04, helper 0.1.2/code3, addresses actual admission failures without relaxing those guards. It retries only null root or missing root-window snapshots, polling at intervals of up to 50 ms within a 2-second elapsed-clock budget. A real non-VNC root or focus/display/geometry mismatch rejects immediately. Synchronous platform queries may themselves overrun that budget. Both freshness checks occur after readiness; retries do not renew the supplied inspection timestamps.

The cross-invocation window-ID equality requirement is removed. IDs are diagnostic observations, including `hold_admission_snapshot`; that status is not an admitted press. Package/focus/display/exact bounds/point/clock checks continue to gate DOWN. A primary RuntimeException now emits bounded `primary_failure` status, including a reason capped at 256 characters and both actual clocks, before framework `finish`. The helper does not suppress a real framework finish failure or use hidden connection-state/disconnect APIs. UiAutomation continues to preserve other accessibility services.

## Official lifecycle evidence and retained failures

The [public window API](https://developer.android.com/reference/android/view/accessibility/AccessibilityWindowInfo#getId()) promises a unique window ID without promising persistence across automation registrations. Current official [AOSP ViewRootImpl](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/view/ViewRootImpl.java) removes and recreates accessibility interaction connections as accessibility enablement changes; [AccessibilityWindowManager](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AccessibilityWindowManager.java) assigns another ID on connection registration. Those upstream sources explain why an ID may change without app-window replacement; they are not an exact source mapping to the installed HP vendor build. The retained private `candidate-04/official-readiness-review.md` records the precise source/API URLs.

The actual installed candidate 03 rejected a missing-mode invocation as intended. Its first explicit inspection crashed in framework `Instrumentation.finish`/`UiAutomation.disconnect` with “Cannot call disconnect() while connecting.” A preceding owned Android CLI instrumentation was still active. The parent retired only that owned CLI instance, verified automation absence, and the same helper APK then returned one successful no-input inspection. The competing registration is relevant context; the primary error masked by framework finish was not captured, and its cause remains unknown. Current [AOSP Instrumentation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/Instrumentation.java) and [UiAutomation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/UiAutomation.java) contain that disconnect state restriction, without proving the preceding device exception's cause.

Two later candidate 03 inspections failed with `active root is not VNC`. That version conflated null root and actual wrong-package root; these are retained **ambiguous root-availability failures**, not proof that another app owned the active root. A fresh WindowManager focus observation does not establish accessibility-root availability at the exact call. Public [`waitForIdle`](https://developer.android.com/reference/android/app/UiAutomation#waitForIdle(long,%20long)) waits for event-stream silence rather than guaranteeing root availability, so candidate 04 adds no idle prerequisite.

The README now requires exclusive UiAutomation ownership: finish the fresh framebuffer/layout inspection first, retire only an identified owned CLI instrumentation, verify its registration is absent, then perform helper inspect/hold without an interleaved CLI layout/interaction command. An unknown automation owner requires stopping. The helper never kills another package.
