## Implementation and review boundaries

The owned `StreamIdentityStore` implements the actual pinned `LimelightCryptoProvider` interface. Explicit enrollment generates RSA2048 inside Android Keystore, with SIGN purpose, the reviewed TLS digest/padding authorizations, a 30-second strong-biometric/device-credential authorization window and an unlocked-device requirement. No private-key file, Console identity, upstream Moonlight credential file or automatic software fallback is used.

An interrupted operation remains visible. A bounded pending record precedes generation; existing, missing, malformed and orphaned identities require an explicit recovery action. The successful enrollment path requires provider-neutral JCA signing of a finite-validity self-signed certificate, with validity, self-signature and public-key match checked before atomic public metadata publication. Qualification is returned only after a real random challenge has been signed and verified; these signing operations have not succeeded in the recorded device attempts. The non-exportability diagnostic checks only for null private encoding; unexpected bytes are wiped and rejected, never recorded. That narrowly scoped diagnostic does not authorize key serialization.

The public certificate and versioned alias metadata reside in credential-encrypted app-private no-backup storage. Diagnostic output omits aliases, certificate bodies, PINs, challenge/signature bytes and private handles. Reported hardware protection comes from actual `KeyInfo`; non-exportability alone is not labelled hardware backing.

Cancellation and attempt replacement immediately invalidate the app's authorization token without waiting on key generation or disk I/O. Provider getters require the same live owner, an unexpired authorization window, an unlocked device and a valid certificate. Cancellation racing an already-started public atomic commit can leave enrollment ready; post-commit checks still withhold the cancelled attempt's provider/result. An opaque handle already returned to upstream cannot be cryptographically revoked by the app lease. Future network ownership must cancel HTTP and prevent stale continuation as specified in the provider entry.

The parent and a separate direct Codex GPT6.1-Sol reviewer examined the store, authorization policy and its three focused tests. The review found a real API-availability defect: `KeyInfo.isUnlockedDeviceRequired()` was added in version36.1, while the initial store admitted API35. The parent restricted identity admission and guarded the inspector at API37 before key creation. The APK's existing native-load minimum remains35; this does not assert identity compatibility on older devices. [Official inspector availability](https://developer.android.com/reference/android/security/keystore/KeyInfo#isUnlockedDeviceRequired()).

## Prompt and lifecycle requirements

Use stable AndroidX Biometric1.1.0, a `FragmentActivity`, and the normal system prompt with `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`. The chosen time-based key route calls `authenticate(PromptInfo)` without a CryptoObject or negative-button override. Construct the prompt during every Activity recreation to reattach callbacks; authorization remains process-memory state and is never restored from a saved boolean. These choices follow [Android authentication guidance](https://developer.android.com/identity/sign-in/biometric-auth), the [stable release](https://developer.android.com/jetpack/androidx/releases/biometric) and [prompt lifecycle contract](https://developer.android.com/reference/androidx/biometric/BiometricPrompt).

A single retained owner serializes crypto and evidence work off the main thread. Actual success callbacks supply elapsed-time authorization timestamps. Explicit cancellation, last-window background and deadline expiry invalidate the attempt before cancelling the prompt. Configuration recreation may reattach an existing prompt but cannot start a new one automatically. Window-focus loss alone is not background, because the system authentication dialog takes focus. No replacement operation is admitted while its predecessor's worker or prompt still needs retirement.

## Actual authentication failure and control

The test device is HP Googlebook14, Android17/API37, arm64-v8a, build `CL3B.260622.276.R2`, incremental `16560795`, security patch 2026-09-01. The historical 0.1.1/code2 Create operation generated the app-owned key. The user confirmed completing the actual system prompt, yet the journal reports `AUTH_REQUIRED` 20ms after its success callback, with no successful signing/enrollment. Refresh retained `ENROLLMENT_PENDING` and actual `trusted-environment` backing. This result remains preserved, not superseded by a claimed fix.

The user confirmed the subsequent 0.1.2 prompt too. This version uses the same pending key and adds a plain provider-neutral SHA256withRSA init/sign/verify control before BC certificate construction. Private `qualification/results/private/native-stream/2026-10-15-identity-02/010a6d3e-98ef-4d39-bd64-fa00f3423e17.json` records authentication type **2** (biometric), success at elapsed 100185871ms and failure at 100185877ms, a **6ms** interval. Actual failure is `AUTH_REQUIRED`, stage `precertificate-sign-init`, cause `UserNotAuthenticatedException`, numeric `keyStoreErrorCode=null`. The pre-control Refresh records remain pending/trusted-environment; no key replacement, completed certificate or qualification result is established. Host connections and decoded frames remain zero. This pre-BC failure localizes the concrete rejection to JCA/Keystore initialization; it does not support changing the BC certificate builder or forcing BC for an opaque key.

Review caveat: the generic `IdentityException` guard wrapper can inherit the enclosing stage label, so a stage field alone may misattribute a guard failure to crypto initialization. This actual cause is `UserNotAuthenticatedException`, not merely guard `IdentityException`; it supports the Keystore/JCA rejection interpretation. A null numeric code provides no underlying Keystore/token/HAL diagnosis. The 6ms and prior 20ms intervals exclude ordinary expiry of the app's 30-second window, without proving Keystore token acceptance or a framework/provider root cause. Prompt success and trusted-environment reporting are separate observations from permission to use the key.

No successful sign/verify, completed enrollment, client TLS, pairing, Sunshine connection or product-vault qualification is claimed. Keep the pending key and fail-closed policy; any subsequent bounded control must target the observed public authentication/Keystore boundary. Compiler/test/Lint success and the user-completed prompts do not promote CAP-STREAM or resolve network cancellation/trust integration.
