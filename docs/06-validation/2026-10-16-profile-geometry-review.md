## Minimal source repair

In `shared/android/platform/src/main/kotlin/io/github/baitian6641/cloudy/platform/ProfileEditorScreen.kt`, a `LaunchedEffect(editorId)` scrolls the existing lazy list to an accepted new/replaced editor. A saveable reveal marker and saveable list state distinguish new navigation from restored presentation. Field text and selection changes retain the editor ID, so typing does not request another reveal. Recreation of that same editor does not deliberately reset the viewport. The effect neither requests focus nor performs storage I/O. Existing message/uncertainty items are included when locating the editor.

In `shared/android/platform/src/main/kotlin/io/github/baitian6641/cloudy/platform/CloudyProfilesActivity.kt`, title, explanation and frozen saved label/protocol/endpoint/revision now share one ordinary vertical-scroll region in the Material dialog text slot. Confirm and Cancel stay in the dialog action slots. Scroll state is keyed to the exact confirmation request, preventing a replacement request from inheriting the prior identity's reading position. The heading keeps the existing titleLarge typography and gains explicit heading semantics; other text retains its existing Material body roles.

This changes presentation only. Owning-app storage, generation/revision comparison, frozen confirmation identity, deliberate confirmation, pending-mutation restoration, foreground interaction checks, pause cancellation and stale Activity callback handling retain their existing contracts. No credential/authentication grant, connection, implicit enrollment or automatic mutation replay is introduced.

The design follows the already-reviewed official [Compose side-effect guidance](https://developer.android.com/develop/ui/compose/side-effects), [lazy-list state/scroll guidance](https://developer.android.com/develop/ui/compose/lists), [scroll guidance](https://developer.android.com/develop/ui/compose/touch-input/scroll/scroll-modifiers) and [dialog guidance](https://developer.android.com/develop/ui/compose/components/dialog). References support the adapter choices; they do not substitute for native evidence.

## Strengthened authored-boundary checks

`testing/foundation/src/androidTest/kotlin/io/github/baitian6641/cloudy/testing/ProfileGeometryContract.kt` contains three opt-in real-manager cases inherited by each app:

- Create bounded synthetic public-endpoint fixtures in the real owning store, edit a catalog target preceded by at least fifteen owned rows, then observe automatic editor/heading visibility **without scrolling after Edit**.
- Use a valid maximum-length saved label/host, preserve an unsaved draft and selection, inspect complete title/body/frozen identity through ordinary ancestor scrolling, require both actions fully visible, then Cancel and verify the exact draft, selection and catalog remain intact.
- Reveal a lower-row editor, explicitly scroll once to the port field, then passively compare viewport coordinates, text/selection and actual framework configuration through typing and Activity recreation. The test requires a genuinely short window that has moved the editor heading above that viewport.

Review strengthened visibility beyond `assertIsDisplayed`, which allows partial visibility: unclipped and clipped bounds are compared with the actual viewport. Long dialog text uses complete line ranges, line geometry, no ellipsis/max-line loss and accumulated fully visible line coverage during scrolling. This avoids demanding that an intentionally scrollable long identity fit simultaneously, or treating a coarse text-layout overflow flag as the sole readability oracle. Tests distinguish dialog geometry from editor navigation; only the dialog lane may explicitly scroll to the editor before its separate observation.

The harness measures actual WindowMetrics, framework font scale/density and Activity configuration; it does not override Compose density/font scaling. Queue settlement, exact catalog/generation checks and fixture-specific revision-bound deletion protect unrelated data. Cleanup closes the Activity and drains work before fixture deletion, restores only captured appearance/density choices, and retains evidence on an unknown result. Baseline pre-mutation receipts and cleanup events are separate from JUnit pass counts.
