## Engine boundary and selected implementation dependency

The new JVM `:ssh` module retains SSHJ0.41.2, ASN-one0.6.0, BC provider/PKIX/utility1.86 and SLF4J API/NOP2.0.20. It uses the reviewed modern P0 policy: `ecdh-sha2-nistp256` KEX, `ecdsa-sha2-nistp256` host signature, `aes128-gcm@openssh.com`, `hmac-sha2-256` configuration and no compression. Factories and negotiated algorithms are both restricted; the domain's five supported key formats do not expand this initial negotiation policy. `DefaultSecurityProviderConfig` disables SSHJ auto-registration before client construction; no Android provider is globally installed or replaced.

The observer accepts a validated logical peer and an independently resolved numeric address, uses only `address.hostAddress`, and checks the callback's exact numeric address/port. SSHJ's maintained `Buffer.PlainBuffer.putPublicKey` serializes the SSH wire key; SHA256 and unpadded standard Base64 produce the domain identity. Cloudy does not hash DER, infer the wire format from a generic Java algorithm name, or use SSHJ's MD5 fingerprint helper.

At selected upstream revision `6fad160fe36605a68847ac8a527750c615b4bd04`, the selected KEX verifies the exchange signature before `HostKeyVerifier` runs; NEWKEYS follows that callback. Cloudy's verifier **always returns false**, including when a saved pin matches. The result is a signed-key observation followed by intentional transport rejection, not a completed handshake, authenticated identity, session or credential-release grant. No authentication, terminal, SFTP, forwarding or trust-store operation occurs inside the observer. Retained source references and broader boundaries remain in [ADR0011](../adr/0011-ssh-terminal-investigation.md) and the [trust contract](../02-architecture/ssh-host-trust.md).

One owned socket is registered with sticky cancellation checks before and after registration. A monotonic total deadline closes it through a bounded watcher. Socket closure precedes SSHClient shutdown. A separate close helper avoids waiting indefinitely for a transport lock on the owning worker; actual Reader, watcher and close-helper joins share a finite two-second cleanup budget. Interrupted cleanup requests cancellation, continues finite retirement and restores the caller's interrupt flag.

The Reader lifecycle mechanism is deliberately a **selected-pin implementation dependency**. The public `Config.LoggerFactory` supplies a non-emitting Reader logger. The exact unconditional `debug("Stopping")` invocation captures the actual Reader thread, including the path interrupted before its first stream read. The host-key callback's thread reference must agree. The protected `doKex` entry follows `TransportImpl.init` and `reader.start`, marking that a Reader is expected. Checked connect/greeting failures before that point do not imply a started Reader; unexpected unchecked setup is conservative cleanup uncertainty. `Transport.join`/`isRunning` are not substituted for actual Thread termination.

Missing/inconsistent terminal evidence, failed closure, abnormal setup or a join deadline cannot produce `SignedKeyObserved`. They produce `CLEANUP_UNCERTAIN` and quarantine that observer instance. The platform keeps its observer across windows so recreation cannot reset this quarantine. All other library loggers remain NOP; exception/server text is not copied into typed outcomes. Changing the SSHJ pin requires rechecking this hook, not merely retaining its old comment.

## Domain, Android and native presentation

`SshObservationPresentation` binds a live in-memory attempt to owner, profile-store generation, exact committed profile/revision and logical peer. Fresh monotonic deadlines, identity-bound completion, one-time approval consumption and synchronized pause/cancel ordering reject stale/expired/changed-profile proposals. Current profile state is loaded again before approval. Trust storage performs its independent generation/revision/reason/previous-key CAS. A later pause cannot undo a CAS already admitted; pending state records uncertainty rather than promising rollback.

Android DNS uses `DnsResolver` with cancellation and finite deadlines; numeric parsing performs no DNS. The API37 constructor is guarded, with the older supported path retained for min35. Late resolution/transport callbacks cannot repopulate a retired operation. The Activity cancels on pause/save/destroy, retires presentations, ignores stale callbacks and restores only schema/owner/pending metadata. Selection, key, attempt, deadline and approval are never restored or replayed. A permission result requires a fresh user action.

The native dialog presents exact peer/route, observed key, prior key when applicable and expected revision. Saving changes only owning-app trust. A subsequent Check opens a fresh observation; it does not resume the rejected connection. Refresh reads current state but does not attribute a prior uncertain save to a specific attempt. Scalable dialog text and fixed actions use the reviewed native presentation pattern; this source review does not establish physical-input or rendered-geometry acceptance.

## Findings resolved before the reviewed build

- **Network prompt heuristic:** the initial address-only prompt suggestion could unnecessarily intercept VPN/cellular routes. Current `SshLocalNetworkPolicy` prioritizes VPN and cellular and suggests permission only for a known local candidate on Wi-Fi/Ethernet. The heuristic never grants access or bypasses Android enforcement; public-looking destinations can still be local under a particular topology. Actual routed permission behavior remains separate qualification.
- **Queued expiry:** an attempt can expire while waiting for the worker. The worker computes the smaller ticket/transport deadline, rejects nonpositive remaining time before calling the engine, and shares that remaining budget across candidate addresses. Only connect failure permits fallback; observed keys, policy rejection and cleanup uncertainty stop it.
- **Permission copy:** resource text says permission “may be needed for this target,” and explicitly requires a fresh action after the prompt. It does not promise that every private address requires a prompt or that grant resumes a check.
- **Lazy test action:** Check is materialized through the parent LazyColumn before `performScrollTo`; direct interaction with a possibly uncomposed actions item is no longer relied upon.
- **Packaged notice provenance:** the copied SSH notice README was corrected from diagnostic/proposed wording to the actual retained observation closure. Binary/source/POM and notice hashes still require exact packaging/graph verification; a corrected README alone is not that evidence.

Independent source review found no blocking observer retirement or trust-admission defect after these corrections. That is a source conclusion, not a replacement for actual tests or an upstream lifecycle guarantee.

## Test meaning and guarded restoration

JVM coverage checks canonical SSH-wire fingerprinting, unsupported keys, exact algorithm policy, cancellation/deadline/worker ownership, missing/wrong-thread retirement evidence and real bounded TCP behavior. The opt-in OpenSSH success case uses an independently supplied public fingerprint. Platform instrumentation exercises the actual resolver and repeated real engine observations plus sticky pre-cancellation. No fixture-dependent success is inferred from default skips.

Each app's three actual-host Activity cases cover Cancel/recreation without trust mutation; first-use Confirm, exact accepted revision1 and explicit fresh Match without rewriting; and stale first-use confirmation after a competing production-store acceptance, requiring CONFLICT with revision1 unchanged. Independent fixture keys, complete baselines/metadata and the only expected deletable row are persisted before mutation. Digest comparisons do not intentionally print fingerprints into assertion messages.

Trust fixture deletion exists only in test source. After Activity closure and actual worker/main fences, the helper acquires the permanent file lock before opening SQLite. It checks UID, file types/symlinks, anchors, metadata/generation, schema and the entire catalog. It accepts either untouched baseline or baseline plus the independently planned exact fixture row; it never reads an unexpected key/revision and blesses it for deletion. The SQL predicate includes all eight row fields and requires count1. Original catalog/metadata must be restored before the fixture profile is removed through its production CAS. Unexpected rows, uncertain operations or unproved settlement preserve fixtures and receipts. Receipts retain failed-case outcome/type even if exact cleanup succeeds. These removals do not add a product delete API or weaken retained tombstones.
