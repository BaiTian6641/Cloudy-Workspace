## What happened, and what remains unknown

Candidate 03's helper 0.1.1 inspect operation failed during `Instrumentation.finish` with UiAutomation still CONNECTING, connection ID undefined and flags 0. Its catch stored the primary runtime failure only in the final result bundle; teardown then threw before that result could complete. **The original connection exception is therefore masked and unknown.** In the pinned implementation, this shape fits an unchecked remote registration failure before flags assignment; it is not evidence of the ordinary callback-wait timeout path.

The parent independently observed its preceding Android CLI instrumentation still active and UiAutomation registered. After retiring only that owned CLI instrumentation and verifying absence, one same-APK inspect retry, with no intervening CLI layout, succeeded without input. That supports an ownership-conflict explanation and a useful serialized operating procedure. It does not recover the lost primary error, prove every failure has that cause or establish an HP framework defect/fix.

Candidate 04/helper 0.1.2 adds bounded missing-snapshot readiness and primary-failure status before finish. It retries only a null root or absent window within a two-second elapsed-clock polling budget, requesting sleeps of at most 50 ms between checks; wrong package, focus, display or geometry fails immediately. Synchronous queries, OS stalls or suspend can overrun the polling budget. This is a local fail-closed observation policy, not an Android guarantee that readiness or retirement occurs within two seconds. The inspected source still requires the desired active/focused VNC root on default display with bounded positive geometry.

Separate no-input inspection/admission observations returned diagnostic window IDs **99 then 110 with identical bounds**. The helper retains each actual ID in its evidence but does not require equality across separate automation registrations. Current package, active/focused/default-display status, exact prior bounds, requested-point containment and both recorded monotonic clock ages remain admission gates. Same bounds do not prove permanent window identity, framebuffer containment or immunity to the final inspection-to-dispatch race. Zero-timestamp hold admission failed before input, retaining its primary failure status; no held-button pass follows from that negative check.

## Operating boundary and stop condition

Serialize automation ownership. Retire only identified parent-owned tooling through normal public process controls, confirm it is absent, then run one helper operation without another layout owner entering between inspection and dispatch. If connection or cleanup fails again, preserve bounded primary stage/class and cleanup evidence separately and stop before input. Do not force framework state, invoke hidden connect/disconnect methods, disable accessibility to bypass inspection or silently retry indefinitely.

Public mouse events may carry explicit primary button state; framework injection acceptance still does not prove VNC admission, native write or host receipt. Only a separately correlated host-down/focus-loss/host-release observation can qualify that named recovery case. Carry forward accepted engine/build/trust/framebuffer checks under D12. No broad framework audit, unchanged upstream rerun, new permission, supported-capability promotion or device/build execution was performed for this source note.
