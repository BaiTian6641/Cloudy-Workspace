## Selected implementation

Use FreeRDP **3.32.2**, exact revision `97eff6ddfbbfaa8e42a126d362686bd001ff8bdc`, with **`WITH_MEDIACODEC=ON`**, `WITH_OPENH264=OFF` and FFmpeg disabled. Keep Android API29 and arm64-v8a for this candidate. The active build uses stable NDK `29.0.14206865` and CMake `4.1.2`; the upstream Android declaration instead names NDK `29.0.13113456` (RC1). The integration leader records the actual tool identities and result. This explicit tool substitution is not an assertion of upstream-toolchain equivalence.

The concrete reason to enable H.264 now is KDE KRdp **v6.6.4**: its [versioned README](https://github.com/KDE/krdp/blob/v6.6.4/README.md) requires the Graphics Pipeline/H.264 client route, while its [Plasma capture implementation](https://github.com/KDE/krdp/blob/v6.6.4/src/PlasmaScreencastV1Session.cpp) selects `H264Baseline`. The earlier decoder-free core configuration cannot be assumed to display this server. Retain `rdpgfx` and the native GDI callbacks in the actual adapter; verify negotiated AVC420 rather than assuming a generic bitmap fallback or AVC444 text quality.

FreeRDP's [Android dependency options](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/cmake/ExternalDeps.cmake) and [inner-build forwarding](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/cmake/ExternalFreeRDP.cmake) support this option directly. Its [codec build](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/libfreerdp/codec/CMakeLists.txt) links Android `mediandk`, compiles H.264 and AAC MediaCodec sources, and labels the backend experimental. This adds no bundled codec-source dependency. Keep unneeded audio and device channels disabled in the first connection. Verify the inner cache/configuration actually enabled the decoder; forcing the H.264 feature macro alone is insufficient.

## Official API boundary

The selected [NDK decoder source](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/libfreerdp/codec/h264_mediacodec.c) uses native byte buffers and `video/avc`, with no Java codec wrapper or output Surface. The [official NDK media reference](https://developer.android.com/ndk/reference/group/media) and [official header](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/media/ndk/include/media/NdkMediaCodec.h) establish these boundaries:

| Symbol or request | Availability and implication | Fallback / qualification |
| --- | --- | --- |
| `AMediaCodec_createDecoderByType`, `AMediaCodec_configure`, byte-buffer dequeue/get/queue/release | Core NDK MediaCodec API21; selected backend uses these for `video/avc` | Actual codec selection and initialization can fail; capture codec name, status and cleanup |
| `AMediaCodec_setParameters` | API26; called by this backend | Parameter changes may be rejected; source handles actual output-format changes, but device resize still needs observation |
| `AMediaCodec_getName`, `AMediaCodec_releaseName` | API28; direct calls without lower-API loading guards | Retained API29 baseline covers these symbols; no older-Android claim |
| `AMEDIAFORMAT_KEY_PRIORITY` | API23; realtime scheduling request uses priority0 | Request does not prove timing or hardware acceleration |
| `low-latency` format key | API30 behavior requested using a literal string | A hint on earlier systems, not a new API30 minSdk requirement or latency guarantee |

`createDecoderByType` can select a platform software codec. Enabling MediaCodec therefore does not establish hardware decode. There is no need to import the upstream profile database or Android application UI to use this native codec.

## Native framebuffer and fallback limits

The backend requests planar YUV420, consumes CPU-accessible output, honors stride, slice height and crop, and exposes I420 planes. NV12 output is deinterleaved into staging I420. The shared [H.264 implementation](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/libfreerdp/codec/h264.c) converts regions through `yuv420_context_decode` into the requested RGB framebuffer. This fits the existing Android `gdi_init(PIXEL_FORMAT_RGBX32)` → dirty rectangles → Bitmap/JNI route; it is not zero-copy Surface rendering.

One concrete device risk merits a bounded check: flexible YUV is assumed to be NV12, and the non-planar branch does not establish arbitrary vendor-layout compatibility. Record actual output color format, stride/crop and changing color/text pixels through the real adapter. Planar19 and NV12 21 are intended layouts; flexible `0x7f420888` still needs observed correctness. Do not invent a replacement conversion until a real mismatch occurs.

FreeRDP tries MediaCodec, then OpenH264, then FFmpeg among compiled backends during H.264 context initialization. It does not transparently switch an active backend after later decode errors. With only MediaCodec compiled, initialization failure must surface honestly as unavailable, followed by cleanup. An actual MediaCodec integration failure is the trigger to consider upstream OpenH264 **v2.6.0**, through the existing [external-build driver](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/cmake/ExternalOpenH264.cmake) and [version pin](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/cmake/DepVersions.cmake), rather than another protocol or codec implementation. That route adds source cloning, upstream patches, NDK/make integration and packaging obligations; it is not part of the first candidate.

## Reused JNI and license boundary

FreeRDP's [root license](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/LICENSE) is Apache-2.0, and the codec file carries Apache-2.0 terms. Selected Android bridge files carry **MPL-2.0** headers, including [android_freerdp.c](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/Studio/freeRDPCore/src/main/cpp/android_freerdp.c), [android_event.c](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/Studio/freeRDPCore/src/main/cpp/android_event.c), [android_jni_utils.c](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/Studio/freeRDPCore/src/main/cpp/android_jni_utils.c) and [LibFreeRDP.java](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/Android/Studio/freeRDPCore/src/main/java/com/freerdp/freerdpcore/services/LibFreeRDP.java). Reuse the maintained bridge selectively, preserving per-file notices and recording copied/modified files; do not classify the entire Android integration as Apache solely from the root license. P1-S4 retains the distribution decision.

MediaCodec introduces no bundled third-party codec artifact, but does not settle AVC patent obligations. If OpenH264 becomes necessary, its [BSD source license](https://github.com/cisco/openh264/blob/v2.6.0/LICENSE) and [Cisco binary/licensing guidance](https://github.com/cisco/openh264/blob/v2.6.0/README.md) must be distinguished; Cisco's provided-binary arrangement cannot simply be assumed to cover a self-compiled library.

## Local KDE prerequisite and practical continuation

A read-only local `apt-get -s install krdp` returned a proposal for **490 upgrades, 22 new packages and 4 removals**, including KWin/Plasma6.5.5→6.6.6 and Qt6.9.2→6.10.2. Private ignored evidence: `.cache/bootstrap/rdp-krdp-install-simulation.txt`; decoder packet: `.cache/bootstrap/rdp-decoder-kde-entry.md`; server research: `.cache/bootstrap/p0-s4-kde-server-research.md`. These are workstation preparation observations, not committed machine inventories or installation evidence. No host package/service/permission change or listener launch occurred. Installing KRdp blindly would modify the running desktop stack substantially, so the leader must select that host change deliberately.

The visible candidate was KRdp6.6.4-0ubuntu1. An [official Ubuntu archive announcement](https://lists.ubuntu.com/archives/resolute-changes/2026-August/029266.html) records a missing-runtime-library fix in6.6.4-0ubuntu2 accepted into proposed; this does not prove promotion into this host's enabled pockets. Resolve the selected package/runtime graph without silently enabling proposed. KRdp also requires an existing logged-in session; preserve the current KDE desktop, deliberate credentials/certificate identity, capture permission and explicit listener teardown. Its [session controller](https://github.com/KDE/krdp/blob/v6.6.4/server/SessionController.cpp) chooses Plasma/portal routes according to build/runtime conditions, so generic portal assumptions are insufficient.

Carry forward the accepted decoder-enabled native build and implement the smallest actual JNI/framebuffer/trust/cancel/input screen while the host fixture is selected. A successful compile closes only the build question. A finite real KDE connection must establish actual graphics negotiation, changing desktop pixels, deliberate authentication/trust behavior, input/focus release and disconnect cleanup. Record performance and physical keyboard/IME separately; baseline4:2:0 plus framebuffer copies do not establish high-quality text or latency. Once that representative route succeeds, continue integration rather than reopening an exhaustive upstream audit.
