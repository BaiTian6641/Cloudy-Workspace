**Checked:** 2026-10-15. **Owner/stage:** Android terminal developer, P0-S3, with independent source and evidence review. **Status:** reviewed diagnostic method and helper source; the subsequent [bounded CDP/device run](../../qualification/results/P0-S3/2026-10-15-terminal-input-trace.md) records actual DOM events and host bytes, with public evidence review tracked there. This note does not qualify CAP-SSH or CAP-TERMINAL, expand production debugging or identify the cause of the existing input failure.

The [ordinary-shell terminal evidence](../../qualification/results/P0-S3/2026-10-15-terminal-probe.md) establishes duplicated host-received bytes from rapid ADB text injection, a bounded paced-input success and a separate native-focus correction. Physical keyboard input, native CJK IME and TalkBack remain separate gates in the [renderer contract](../03-platform/googlebook/p0-s3-terminal-renderer-increment.md).

## Official debugging guidance and availability

`WebView.setWebContentsDebuggingEnabled(boolean)` is available from API 19. Its current reference states that WebView **113.0.5656.0 and later** enable debugging automatically for manifest-debuggable apps. The selected diagnostic is a debug build, and the device run recorded provider **149.0.7827.5**. The follow-up verified the existing own-process socket/target without another APK or debug-enabling call; availability still requires a scoped check on each different runtime. [Android WebView API](https://developer.android.com/reference/android/webkit/WebView#setWebContentsDebuggingEnabled(boolean))

Both the older Chrome guide and the Android guide updated **2026-02-26** say the manifest flag does not affect WebView debugging. Those statements conflict with the API reference's explicit version rule. Prefer that version-specific rule, then verify actual runtime availability; a newer guide timestamp alone does not settle a semantic contradiction. This diagnostic adds no production permission, unrestricted bridge, provider flag or debug-enabling call. If the exact own target is unavailable, record an unavailable diagnostic and retain the existing input failure. [Chrome WebView guide](https://developer.chrome.com/docs/devtools/remote-debugging/webviews), [Android DevTools guide](https://developer.android.com/develop/ui/views/layout/webapps/debug-chrome-devtools)

Upstream Chromium formats its abstract WebView socket from the process PID. The inspected source is commit `9120d433b45e13d916ca105edba4f94734981db7`, file `android_webview/browser/aw_devtools_server.cc`, SHA-256 `cbe4ffdf058d8272ee8db4ed84f7ef80660c0912bdc8c762a71fd4262a8a7147`. ## Interpretation and remaining uncertainty

R106's pinned xterm 6.0.0 source, commit `f447274f430fd22513f6adbf9862d19524471c04`, schedules deferred textarea-difference handling for some non-composing key-code-229 events. Closely spaced callbacks are a plausible duplication mechanism, not an observed cause. The composition source hash remains `270ea7fa05ebb48e14f50a63dd61e0230f36f40f4d0232579e4b884d8579ed99`. [Pinned CompositionHelper](https://github.com/xtermjs/xterm.js/blob/f447274f430fd22513f6adbf9862d19524471c04/src/browser/input/CompositionHelper.ts#L186-L206)

The first trace deliberately leaves xterm callbacks, `cloudyTerminal.postMessage`, timers and encoders unchanged. Its lexical `onData` path is not passively observable through an existing public bridge hook. DOM progression plus host bytes can narrow the investigation, but cannot establish the exact emitted callback/frame sequence or exclude every intermediate contribution. Added listeners have timing overhead; record any difference between instrumented and uninstrumented behavior. A browser event's `isTrusted` does not distinguish ADB injection from physical typing. An incomplete trace, missed capture window or target loss remains inconclusive. No input deduplication, accessibility disabling, custom IME or second native key-forwarding path is justified by this research alone.
