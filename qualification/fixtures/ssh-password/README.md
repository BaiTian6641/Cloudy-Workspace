# Isolated SSH password fixture

This is an implemented maintained-library host fixture for Cloudy's finite password-authentication adapter. It uses Apache MINA SSHD2.20.0 to perform genuine SSH negotiation, encryption and userauth. It is not OpenSSH, PAM, a system account or production-server qualification. No account or host SSH policy is modified. The integration leader owns dependency verification, compilation, execution, evidence and acceptance; the [qualification report](../../results/P1-S3/2026-10-16-ssh-authentication.md) records strict fixture compilation and10 final actual host cases, with the first failed rekey expectation preserved.

## Dependencies and reviewed API pin

Use host/test scope only: `org.apache.sshd:sshd-core:2.20.0`, its `sshd-common:2.20.0` dependency, and the already selected `org.slf4j:slf4j-api:2.0.20` plus `slf4j-nop:2.0.20`. The fixture refuses startup unless the active logger factory is NOP. It uses the default built-in NIO2 backend, not a separate MINA/Netty transport. These dependencies are not product runtime additions. The leader verified and froze actual artifact hashes in [dependencies.json](dependencies.json). The Apache binary ZIP matches its published SHA512, and contained core/common JARs match the selected Maven bytes; SLF4J JARs match their published SHA512. No artifacts are vendored here and no PGP-signature verification is claimed.

The official [Apache downloads page](https://mina.apache.org/downloads-sshd.html) lists2.20.0 as the stable release;3.0.0-M6 is a distinct prerelease. The [2.20.0 tag](https://apache.googlesource.com/mina-sshd/+/refs/tags/sshd-2.20.0) resolves to commit `2221febd396cd3daafdfbf2ff982c6d0eb69a203`, tag object `5b03bf38e50f29339fd3d211d921912c49bb9dc0`. ## Launch and private provisioning contract

After the leader compiles the single source against the verified classpath, invoke `CloudySshPasswordFixture` with exactly one argument: a **new, nonexistent** output-directory path whose parent already exists. The fixture atomically creates that leaf with POSIX700 and files with POSIX600; it refuses to reuse or chmod an existing directory. Runtime credentials/evidence belong outside tracked files. Do not publish `fixture.properties` or generated credentials.

It binds only127.0.0.1 on ephemeral port0. Standard output contains one readiness line with only port and SHA256 host fingerprint; failure output is the fixed `FIXTURE_FAILED` token. The private `fixture.properties` contains exactly these keys:

| Key | Meaning |
| --- | --- |
| `port` | Selected loopback TCP port |
| `fingerprint` | Exact generated ECDSA SHA256 fingerprint |
| `password` | Random32-byte, base64url encoded, fixture-only secret |
| `user.accept` | `fixture-accept` |
| `user.deny` | `fixture-deny` |
| `user.change` | `fixture-change` |
| `user.wait` | `fixture-wait` |
| `user.close` | `fixture-close` |
| `user.rekey` | `fixture-rekey` |

The parent's external-fixture tests use `CLOUDY_SSH_AUTH_FIXTURE` pointing to that private properties file. The implicit address is127.0.0.1. Fixed usernames are synthetic routing selectors, not operating-system users. The fixture password is shared only among its six synthetic modes. Maintained server APIs receive immutable Java password strings, so complete heap zeroization is not claimed; process exit bounds this fixture lifetime.

The accept lane accepts only the generated secret. Deny always rejects. Change requires that secret then throws the upstream password-change exception; any changed-password request is counted and denied. Wait requires that secret then remains asynchronously incomplete until client disconnect, server shutdown or the finite server lifetime. Close and rekey also require that secret and remain asynchronously pending with no accept/deny response: the close lane requests actual `ServerSession.close(true)`; the rekey lane requests actual `session.reExchangeKeys()` without resolving authentication. Both actions are scheduled100ms later on the server-owned scheduled executor, outside `ServerUserAuthService.process`'s synchronized auth path, with no blocking wait for KEX. Pending scheduled futures are tracked and cancelled on session closure/server shutdown; no new worker thread is created per request. Wrong passwords and unknown users deny. There are no shell/command/subsystem implementations; all session channels and forwarding are rejected. Every channel-open request is separately counted before library dispatch.

Normal operation ends after at most175seconds followed by up to four seconds of close waiting. A shutdown hook performs the same close. An absolute180second watchdog includes startup and cleanup; exit124 is forced termination/uncertain cleanup, never a pass. Exit0 requires confirmed server closure with no evidence I/O failure or cap overflow; exit2 means incomplete closure/evidence. The parent must record exit and independently check listener/process retirement. Temporary private outputs are retained for the parent's exact-path cleanup.

## Safe metadata and assertions

`events.jsonl` records bounded metadata only: event, numeric fixture-local session index, synthetic mode `accept|deny|change|wait|close|rekey|unknown`, method allowlist `none|password|publickey|keyboard-interactive|other`, and `passwordChange` only for password requests. It never records username, password, server prompt, packet payload, address or exception text. Read complete JSONL lines; a concurrent append can momentarily expose a partial final line. `summary.json` is atomically replaced with aggregate counters, evidence flags and `serverClosed`. Limits are64 sessions and512 events; overflow or I/O failure invalidates evidence. These caps are fixture bounds, not server security/load qualification.

Correlate each result with its session index. A protocol `none` discovery request is recorded separately and must not be confused with a password attempt. For password-change refusal require exactly one password request with `passwordChange:false`, one `change_required` event, zero changed-password requests, zero keyboard-interactive/public-key attempts, zero channels and actual session closure. `change_required` means the authenticator requested the upstream challenge; client typed refusal corroborates actual receipt of USERAUTH_60. Do not relabel that event alone as proof the challenge reached the client.

For close require one initial non-change password request, `close_requested`, no `auth_accepted`/authenticated event, actual `session_closed`, no retry/fallback and a typed client failure with confirmed retirement. The original pre-authentication rekey case expected the client's second host-key callback to reject. Host01 remains a failed9/10 run: it timed out, and no second key-established event was observed. Source inspection explains why: selected SSHJ0.41.2 permits another KEX only when initial KEX is incomplete or transport authentication is complete. An asynchronously pending password response leaves neither condition true. Do not reinterpret that timeout as a passing second-key rejection. A separately maintained authenticated, channel-free connection would be needed for the eventual second-callback wire probe; the finite authentication adapter immediately retires after success.

The final host03 limitation case distinguishes server transmission from client participation: require one initial non-change password request, one `server_rekey_kexinit_written`, zero `server_rekey_kexinit_write_failed`, zero `client_rekey_kexinit_negotiation_start`, no second password/change/keyboard-interactive request, no channel, typed finite client timeout and confirmed client/server retirement. Also require the initial negotiation/write for that same fixture session. `rekey_started` alone proves neither write completion nor another exchange. `action_failed`, `action_cancelled`, duplicate-action or write-failure events invalidate the intended lane observation. Host02 and finalhost03 execute10/10 cases; host03 corrects a redundant negative-event name and additionally freezes compiled fixture-class hashes. Their detailed receipts and limits are in the qualification report.

## Public KEX evidence hooks and exact semantics

The outgoing hook is maintained `ReservedSessionMessagesHandler.sendKexInitRequest(Session, Map, Buffer)`. It receives the complete already-encoded plaintext KEXINIT payload, including its opcode, and a nonnull return transfers delivery responsibility. The fixture obtains a copy using `packet.getCompactData()`, leaves the original read/write positions and bytes untouched, and creates a fresh maintained packet with `session.createBuffer(SSH_MSG_KEXINIT, payload.length)`. That API reserves framing and writes the opcode. `putRawBytes(payload,1,payload.length-1)` copies the remaining existing payload without serializing any SSH field. `session.writePacket(outgoing)` performs upstream framing/encryption/I/O; the hook returns that exact actual `IoWriteFuture`, preventing duplicate fallback transmission.

This copy is an invariant, not cosmetic: in the selected source JAR, `AbstractSession.java:1829–1840` invokes the hook **before** extracting the original payload as exchange-hash input; `doWritePacket` at1175–1184 encodes/mutates the supplied buffer. Writing the original inline could corrupt that hash input. No payload, key-exchange proposal or transcript is recorded.

Each session's first outgoing invocation yields `server_initial_kexinit_written` or `server_initial_kexinit_write_failed`; later invocations yield `server_rekey_kexinit_written` or `server_rekey_kexinit_write_failed`. These events are emitted from the actual I/O future listener using `isWritten()`. Successful write completion means the library's underlying I/O write completed; it does not prove remote receipt, acceptance or KEX completion.

Incoming evidence uses public `SessionListener.sessionNegotiationStart`, naming first/subsequent callbacks `client_initial_kexinit_negotiation_start` and `client_rekey_kexinit_negotiation_start`. In the selected source, `AbstractSession.java:879–884` handles KEXINIT by parsing it then starting negotiation; `negotiate()` at2186–2189 emits the callback through `SessionHelper.java:1093–1118`. It establishes that a parsed peer proposal reached negotiation. It is **not** raw encrypted packet ingress accounting: malformed/aborted traffic before that callback is outside the count. No proposal contents are inspected. Initial/rekey event classification is per fixture-session invocation order, independently of when synthetic account mode becomes known.
