## Integrity, algorithms and provider observations

The unchanged sentinel was **28 bytes**, SHA-256 **`114d3935955b73a27a64f51412c84f668f2054e96f66ad07114de44682bfc6b6`**. Both retained new files were **65,536 bytes**, each SHA-256 **`f8a38b49873588eea0fa55c178b2ad20a05eb7f3eccf55623323405fdec79fe9`**. The evidence author compared every actual payload byte with `(31 × index + 17) mod 256`, independently of the app's report. The successful attempt IDs are `f4adff9e-128e-4f0f-9389-2bad58ac8685` and `57e4e169-a051-4193-a1bd-6e353e6f9197`.

Both completions used **SFTP version 3**. The second `WRITE | CREAT | EXCL` request returned generic **`FAILURE`**; the subsequent length/hash read confirmed unchanged original bytes. This proves the observed refusal and retained contents for this fixture, not that every future `FAILURE` means file-already-exists. No overwrite, rename, conditional replacement, atomic publication, remote deletion, fsync or crash-durability result is supplied.

The recorded negotiated fields were `ecdh-sha2-nistp256`, `ecdsa-sha2-nistp256`, `aes128-gcm@openssh.com` in both directions and `none` compression. `hmac-sha2-256` appears as the proposal field; **AES-GCM uses its own authentication tag, so a separate MAC was not used**. These observations exercise SSHJ **0.41.2**, aligned BC **1.86**, SLF4J API/NOP **2.0.20** and asn-one **0.6.0** with the generated unencrypted SEC1 EC PEM fixture key. They do not qualify arbitrary key formats or the full product algorithm policy.

All ten selected journal snapshots report the same provider names/order as at runtime creation. The manifest retains both lists, including the pre-existing platform `BC` entry. Equality at these observations does not attest to every provider implementation or exclude transient changes between samples; the reviewed app code makes no global provider mutation.
