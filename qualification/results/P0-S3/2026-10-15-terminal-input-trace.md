## Interpretation and remaining experiment

The observed DOM path inserted four characters while the host received ten in both bulk cases. R106's pinned xterm **6.0.0** `CompositionHelper`, commit **`f447274f430fd22513f6adbf9862d19524471c04`**, defers textarea-difference handling for some non-composing key-code-229 input. A model in which four callbacks retain old values `""`, `s`, `st`, `stt` and each later reads `stty` would emit **`stty` + `tty` + `ty` + `y`**, exactly the observed ten-byte sequence. This is a source-consistent hypothesis, not an observed callback sequence. [Pinned upstream source](https://github.com/xtermjs/xterm.js/blob/f447274f430fd22513f6adbf9862d19524471c04/src/browser/input/CompositionHelper.ts#L186-L206)

This run did not observe xterm `onData`, deferred callback execution, encoded bridge frames or individual native writes. It cannot conclusively assign responsibility to any one boundary. The fresh untraced comparison shows that active trace listeners were not necessary for duplication in that sample; it does not establish zero observer effect or identical scheduling. A subsequent [exact-source scheduling experiment](../../../docs/07-reference/2026-10-15-xterm-input-fix-candidate.md) reproduces this mechanism and compares the official upstream candidate. It is separate software evidence and does not retroactively observe the device callbacks. No input deduplication, second native key-forwarding path, custom IME or accessibility disabling is accepted from these results.
