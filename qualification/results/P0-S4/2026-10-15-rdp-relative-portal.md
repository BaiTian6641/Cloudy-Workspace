## Server finding and next experiment

The official [KRdp6.4.5 input handler](https://github.com/KDE/krdp/blob/v6.4.5/src/InputHandler.cpp) registers absolute/extended mouse and keyboard callbacks, but no standard `RelMouseEvent` callback. This is a concrete server-side gap consistent with the observed no-motion result; the experiment did not capture decrypted wire events. Normal portal authorization fixed the earlier permission boundary, but cannot add an absent protocol input handler. Keep the standard client implementation and choose an actually compatible server/version for the next relative-input test. A new desktop environment, server install or host backport is a separate reviewed action; do not silently change the user's session.

FreeRDPserver3.32.1 [defaults relative capability on](https://github.com/FreeRDP/FreeRDP/blob/3.32.1/libfreerdp/core/settings.c); its [relative receive path](https://github.com/FreeRDP/FreeRDP/blob/3.32.1/libfreerdp/core/input.c) uses a [nullable callback macro](https://github.com/FreeRDP/FreeRDP/blob/3.32.1/include/freerdp/api.h) whose supplied default is TRUE. Thus an arriving event can be discarded successfully when KRdp has no handler. Inspected [KRdp6.8.0](https://github.com/KDE/krdp/blob/v6.8.0/src/InputHandler.cpp) also lacks that registration; an upgrade alone is not a demonstrated repair.

A source-supported next candidate is GNOME Remote Desktop50.2 at `60423c896a54e3eacb65bd93167e91c1ce5e648c`: its [RDP callback](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/src/grd-session-rdp.c), [event queue](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/src/grd-rdp-event-queue.c) and [libei dispatch](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/src/grd-session.c) implement a standard relative consumption chain. Its [Mutter/libei/PipeWire requirements](https://github.com/GNOME/gnome-remote-desktop/blob/50.2/README.md) require a separate suitable session or headless fixture. It is not installed or qualified, and does not replace the current KWin session. A suitable Windows RDP host is another future lane.

The [RDP desktop contract](../../../docs/04-design/desktop-rdp-interaction-contract.md) retains Linux, Windows and macOS server-specific lanes. Windows/macOS are not tested, and a macOS RDP server remains unselected. The [credential security contract](../../../docs/02-architecture/rdp-authentication-security.md) remains proposed product work; temporary private fixture provisioning is not the saved-credential vault.
