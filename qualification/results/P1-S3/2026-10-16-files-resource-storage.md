## Implemented behavior

`FilesResourceRegistration` supplies immutable receiver-private metadata with four distinct canonical v4 identifiers, exact account name, unmodified starting-directory spelling and complete local profile/accepted-trust snapshots. A new tuple is PRIVATE at revision1. Explicit share advances it to SHARED; revoke retains the original tuple and bindings as a tombstone. No reactivation, retargeting, automatic profile following or identity reuse operation exists. The navigation root does not confine the remote account or establish a stable server object.

`FilesResourceStore` implements actual owning CE/noBackup SQLite load/create/share/revoke/resolve with generation/revision CAS, exact tuple matching and current profile/trust checks. Real profile editing/deletion and key replacement/revocation make old bindings stale. Reaccepting the same key at a new revision does not revive them. Revocation remains available for stale records. The shared coordination lock orders store checks against current profile/trust mutations; persistence does not yet register or retire any resource-bound live session.

The store retains permanent generation anchors and tombstones, refuses missing/corrupt established storage without reset/deletion, validates canonical rows and metadata, and applies the existing DELETE/EXTRA SQLite policy. Limits are512 retained rows and4MiB database size, excluding journal/filesystem overhead. Nonblocking contention and possibly completed writes have fixed Busy/Completion unknown results. Stored metadata does not prove actual listing, deliberate user consent or IPC caller authority.
