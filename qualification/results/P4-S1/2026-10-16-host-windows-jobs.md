## Actual operation and ownership

The implementation uses existing `golang.org/x/sys/windows v0.49.0` wrappers to create a fresh unnamed noninherited Job Object with `KILL_ON_JOB_CLOSE`, then `CreateProcessW` with creation-time `JOB_LIST` and an exact three-child-handle `HANDLE_LIST`. It does not launch first and assign later, retry outside containment or assume that Go `Cmd` exposes a suspended primary-thread handle. Documented assignment/nesting/API failure is a refused/failed operation with retained owned resources.

Exact process/thread handles are retained immediately after successful creation. If subsequent setup fails, an actual process plus error still gets exactly one shared process waiter and owned termination. The first safe failure survives later wait errors; nil process/nil error is rejected. The parent found an environment prefix-ordering defect during source review; sorting now compares validated variable names, with an A/A0 regression. UTF8/NUL checks, explicit argv escaping, final UTF16 caps, case-insensitive duplicate names and a nonnull exact empty environment are implemented without ambient `SYSTEMROOT` injection.

Actual direct-process wait and DWORD exit status precede a250ms pump observation. A descendant-held pipe cannot postpone the direct-exit trigger to the full runtime merely to await EOF. `IOCompletion` reports that observation separately: an unresolved pump is not a complete drain. Confirmed retirement additionally requires the owned job's actual zero active-process accounting, pump joins and successful owned close operations. Close requests retain asynchronous completion state; a stalled or failed close remains uncertainty under the same owner. Raw-handle close is attempted once rather than blindly retried after potential reuse. These are implemented paths, with Windows runtime behavior still unrun.

The only shared/Linux changes remove fd from the generic containment interface, require its private capability before Linux command construction, and preserve a created process returned with an error. Linux `Start` signature is unchanged. Shared lifecycle tests establish those state/ownership boundaries with doubles, not actual Windows processes.

## Remaining concrete native work

The opt-in test executable contains seven proposed native cases: specific-job membership and exact-handle creation time/cancel; Unicode argv/environment/stdin; exact empty environment; real exit259; direct-parent exit with a pipe-holding descendant; bounded output/blocked input timeout; and exclusion of an unrelated inheritable event handle. Execute them only in a separately reviewed finite parent-owned safety fixture with exact source/binary binding. Stop at the first failed/uncertain case and retain all owners.

The membership case holds a controlled child alive while its retained process handle prevents PID reuse and queries its specific Job Object; membership in a CI outer job alone is insufficient. It is test corroboration, not a product check that rejects legitimate already-exited children. The descendant marker proves successful creation/held pipe handles, not necessarily that descendant user code reached READY. The sentinel may conservatively fail if its numeric handle aliases a new child handle; parent-only inspection is not absence evidence.

Restrictive nested-job refusal with no child marker and native injected post-create/query/termination/close-error ownership cases are not yet implemented/executed by that seven-case suite. Actual Windows handle inheritance, output/drain, cancellation/retirement timing and kernel-stall behavior remain native gates. Same-user path mutation, concurrent uncoordinated broad-inherit spawns, supervisor crash/restart recovery and hostile-user sandboxing remain explicit limits. Ordinary SSH stays independent; remote admission, idempotency/events, packaging and user-session adapters remain separate roadmap work.
